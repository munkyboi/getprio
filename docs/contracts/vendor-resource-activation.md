# Vendor resource tracking activation v1 — explicit local/staging capability

`POST /api/vendor/tenant/:tenantSlug/locations/:locationSlug/resources/:poolId/tracking/activate`

This is distinct from the legacy fixture `/resources/:poolId/activate` endpoint. Legacy route/service/marker/loopback rules and DTO are unchanged. The new capability does not depend on a four-court marker or relabel a fixture.

## Release boundary

Server default OFF. All three must be explicit: `VENDOR_RESOURCE_ACTIVATION_ENABLED=1`, `NODE_ENV=development|test`, `LOCAL_API_PROFILE=core`. Production mode and other profiles remain unavailable even with the flag set. A client flag cannot enable it. Capability is `vendor-resource-activation-v1` under configuration `resourceActivation`; `localActivation` remains separate. Ordinary pool creation stays untracked/defaultFALSE. Enabling tracking does not grant booking access, publish admission, extra subscription capacity, credits or plan changes. Existing Free/Pro permissions, resource limits, publish/booking entitlement services remain authoritative and unchanged.

## Command

Normal authentication, privileged MFA and CSRF middleware apply. Active owner/admin membership must hold both `tenant.location.manage` and `tenant.service.manage` for the active tenant/location. Staff cannot activate, including assigned staff. Owner/admin manage their permitted tenant locations; no fabricated staff assignment is created.

Body is exactly `{expectedPoolRevision: string, configurationVersion: sha256}` plus `Idempotency-Key`. Pool ID/revision are positive decimal strings; unknown fields and missing keys fail400. Stale pool/config revisions fail409. Scope/authorization are checked before receipt replay. Existing location-first resource transaction serializes edits and locks current grants; scope/pool revisions are reread. Current archived/capacity/member/requirements/service-policy/required-extra/workflow feasibility and active allocation/Queue protection/booking-promise blockers apply. The command never repairs inconsistent setup or bypasses live work.

Idempotency uses existing `queue_plan_command_receipts` with distinct action `vendor_resource_pool_activate`, actor/scope/target/payload hash. Same key/payload replays exact recorded result with no new update/audit/event; changed payload conflicts409. Transaction changes only pool tracking+revision and ledger revision, then records `vendor.resource_pool.activate` through `securityAuditService` using the **same client/transaction**, including actor, pool, location and before/after revisions without customer PII. Audit or commit failure rolls back tracking and receipt; SSE `queue-plans-updated` publishes only after a successful commit.

## Schema preparation

`20261025_vendor_resource_activation.sql` drops only `resource_pools_tracking_disabled_check`. FALSE default, capacity constraints, scoped foreign keys and other constraints remain. It contains no data updates and does not enable existing pools. Migration order explicitly depends on resource foundation/ledger, receipt, member/policy and security-audit migrations; tracked Docker manifest is generated by the shared planner. Capability requires receipt and audit tables plus absence of the disabled-only constraint.

No migration execution is authorized by the source change. Ikan needs a separate reviewed local target/backup/rollback lease. Rollback starts by disabling the server flag and preserving recorded allocations/protection; readding a disabled-only constraint is unsafe if legitimate tracked rows exist. Do not silently disable resources or erase audit/receipts to roll back.

## Client compatibility

The activation client selects an available real capability and new route. Only an explicit available legacy fixture capability selects the legacy route. Unknown/unavailable/blocked capability fails closed. An uncertain request preserves the same route, key and revision body for retry; no new key is invented after a transport failure.

## Verification boundaries

Actual `src/app.ts` mounted tests use real auth/MFA, existing resource transaction, receipt and security-audit repository code against a mocked PostgreSQL transport. They cover feature/profile/production negatives, missing auth, foreign tenant, staff/revoked/inactive access, revisions, malformed fields, existing live/protected demand, policy/member setup, same-key replay/conflict, audit/commit rollback and postcommit SSE. Frontend tests cover capability route selection and retry identity. Migration planner tests preserve exact manifest and removal-only SQL shape.

These checks are not actual PostgreSQL/concurrency/schema execution, normal Free/Pro end-to-end setup, production release or runtime activation proof. Those remain independent QA/Ikan gates. No existing service, retained account, provider, runtime environment or database is modified during implementation.
