# Resource pool lifecycle and named-resource administration

Local implementation and browser acceptance slice, 2026-10-17. No PR or production activation is authorized by this evidence.

## Delete and archive contract

Authenticated Vendor Admin GET/PUT `/api/vendor/tenant/:tenantSlug/locations/:locationSlug/resources` retains existing configuration operations. Every pool now includes `archived_at: string | null` and:

```ts
interface PoolDeletion {
  allowed: boolean;
  reasonCode: 'RESOURCE_POOL_REFERENCED' | null;
  message: string;
  dependencies: Array<{ code: string; count: number; label: string }>;
  archiveAllowed: boolean;
  archiveBlock?: { code: 'RESOURCE_POOL_WORKFLOW_IN_PROGRESS'; message: string; affectedRequests: number };
}
```

Counts describe reference rows, including history, rather than a unique customer, service or resource count. They contain no cross-branch identifiers or customer data. Dependency groups cover service requirements, named members and versions, reservations and allocations including historical states, drafts and draft audit, published plans, selection/stage/group history, structured policy references and command history. Structured `poolId`/`pool_id` fields inside frozen JSON are checked recursively; unrelated numbers and matching human-readable names are not references. Drafts containing only service intent do not acquire an invented pool binding: an existing mapped requirement or named member is itself a reference, and captured pool identities remain protected after mappings change.

PUT uses body `{action:'deletePool'|'archivePool',poolId,version,operationKey}`. Success returns the same full configuration shape. The body key is distinct from the named-member API's header key. Same actor/scope/key/body replays the committed response even after deletion; changed payload with the same key returns `409 IDEMPOTENCY_CONFLICT`. New operations require the current GET version (`409 STALE_REVISION`). Missing scoped pool returns 404; current authorization requires both location-manage and service-manage permissions and current branch/actor grants. A referenced delete returns `409 RESOURCE_POOL_REFERENCED`, `message` and `poolDeletion` with the same authoritative structure. Clients must refetch after a race rather than inventing dependency counts.

Deletion requires zero references. The transaction serializes branch writers, locks the scoped pool before its final dependency scan, and retains an actor-linked lifecycle tombstone and response receipt. The requirement FK is RESTRICT, replacing the original cascade. A concurrent FK insert either commits before the final scan and blocks deletion, or waits for deletion and fails its FK; it is never cascade-erased. Existing branch-scoped JSON writers share the branch transaction boundary. Pool lifecycle audit is retained after deletion without a cascading pool FK.

Archive sets timestamp/actor and advances the pool revision; repeated archive is harmless. It does not delete mappings, named members, snapshots, reservations, allocations or history. Archived pools remain visible for administrative history. Creation/editing of named members, requirement assignment, new captured resource demand, Call, Start and allocation-producing Retry reject archived resources. There is no implicit unarchive or automatic reassignment. Tracking is not disabled to bypass validation.

## Protected and already-started work

Archive never frees resource protection or occupancy. A called, protected request fails Start with `RESOURCE_POOL_ARCHIVED`, with guidance to cancel unstarted protection and amend to active resources. Existing five-minute unstarted expiry remains available. The explicit `POST /api/vendor/tenant/:tenantSlug/queue/plans/:planId/cancelProtection?location=:locationSlug` uses `Idempotency-Key` and `{expectedTicketRevision,expectedPlanRevision,currentStageId,expectedStageRevision,reservationGroupId,reason}`. It requires queue-operate permission and current scoped V3/V4 called/unstarted state. The complete exact protection group is cancelled atomically and children, stage and ticket return to Waiting; the command records the actor, reason, old/new snapshots and replay result. Changed-key payload conflicts, stale versions, wrong groups and started allocations reject. Published V3/V4 `allowedActions` includes `cancelProtection` only for an eligible unstarted current protected group. It is an explicit action, never an archive side effect.

Archive is rejected with `409 RESOURCE_POOL_WORKFLOW_IN_PROGRESS` if an already-started parent still requires this pool for a nonterminal future stage or retry, because post-start rebinding is not supported. GET supplies `deletion.archiveAllowed:false` and the scoped `archiveBlock` reason. Completed/resolved stages and obsolete attempts do not block archive. This prevents stranding a parent without introducing implicit restore, rebind or allocation bypasses.

Already-started child Complete/Interrupt uses recorded allocation IDs and can finish after archive, including required-extra resolution and parent completion. Archive does not cause a parent-completion deadlock. Retry is new allocation and remains blocked. Group cancellation cannot cancel or release started work.

## Named resource API reused

- GET `/api/vendor/tenant/:tenantSlug/queue/resource-members?location=:locationSlug&poolId=:poolId` returns `{pool:{id,name,capacity,archived_at},members:[{id,name,revision,isActive,archivedAt,availability:{state,provisional,observedAt}}],holdsCreated:false}`. Archived-pool history remains readable.
- POST the same route with `{poolId,name,isActive}` and `Idempotency-Key` creates a stable UUID and initial immutable version.
- PATCH `/resource-members/:memberId?location=:locationSlug` with `{name,isActive,expectedRevision}` and `Idempotency-Key` returns `{member:{id,poolId,name,revision,isActive,archivedAt},holdsCreated:false}`.

Renames preserve UUIDs and all frozen selections. `isActive:false` disables a member reversibly without erasing versions; PATCH with `isActive:true` can re-enable the same UUID, subject to current revision, capacity and busy guards. This is separate from both explicit member archival and pool archival. No member hard-delete API is introduced. Names are trim/case-insensitive unique within a pool, including inactive rows (`RESOURCE_NAME_CONFLICT`). Active count cannot exceed configured capacity (`RESOURCE_CAPACITY_EXCEEDED`); no operation automatically grows or shrinks capacity. Current named protection/occupancy, and anonymous pool usage with unknown member identity, block member edits/deactivation (`RESOURCE_IN_USE`). Stale revisions return `STALE_REVISION`. Archived pool writes return `RESOURCE_POOL_ARCHIVED`. Permission and branch scope remain server-authoritative.

## Reversible named-resource enable/disable

The existing member PATCH contract supports the toggle; no new endpoint, DTO, migration or runtime restart is required. A disabled member remains in the administrative registry with `isActive:false` and `availability.state:inactive`. Catalog choices retain that explicit flag for consumers to hide or disable, while fresh named capture rejects it with `NAMED_RESOURCE_REQUIRED`. Current member activity and captured member revision are revalidated at Call/Start. Disabling and then re-enabling cannot silently resurrect an old published capture: explicit amendment/review captures the new revision.

This setting governs named selection only. Configured pool capacity stays unchanged; automatic anonymous pooled demand continues to use that separately configured capacity, even when the number of enabled named members is lower. Derived physical effective capacity is a separate unapproved policy change. Do not claim global assignment exclusion from this toggle. Enabling checks the enabled-member count against the existing capacity; it does not increase capacity.

Both named and anonymous pool protection/occupancy block member edits with actionable `RESOURCE_IN_USE`; no toggle releases a reservation or allocation. Role/scope/revision guards and actor-scoped exact-command replay apply. Concurrent enables serialize the last available named-member slot, and concurrent commands on the same member reject stale revisions. Historical names, UUIDs and frozen plan snapshots remain unchanged.

## Independent named-resource archival — clarified contract

Temporary maintenance/leave uses `isActive:false`; explicit archival uses a separate server-owned `archivedAt`. Active collection means `archivedAt === null`, including inactive members shown gray/readable and eligible for re-enable. Archived collection includes only an actual archive timestamp. Archive preserves the last maintenance preference, UUID and name: an archived row can have `isActive:true` while being ineligible for named use. Enabled-member capacity counts only `isActive && !archivedAt`; configured anonymous pool capacity stays unchanged.

Migration `20261017_named_resource_archival.sql` adds nullable archive timestamp/actor to current members and immutable member versions, without changing existing maintenance flags or inventing historical archive dates. Old inactive versions remain inactive with no recorded archive. New explicit archival is recorded as a new actor-linked version. The database capacity trigger excludes archived rows from enabled-member counts.

Dedicated POST `/api/vendor/tenant/:tenantSlug/queue/resource-members/:memberId/archive?location=:locationSlug` accepts `{expectedRevision}` plus `Idempotency-Key`. It returns `{member:{id,poolId,name,revision,isActive,archivedAt},holdsCreated:false}`. Same-key replay preserves the original response; changed payload conflicts, stale revisions and wrong scope reject. New-key archive of an already archived current revision is a no-op. Archived member PATCH rejects `RESOURCE_MEMBER_ARCHIVED`; no restore endpoint or implicit re-enable is introduced. Archived resources stay readable. New registry/options responses always expose `archivedAt`; historical stored PATCH replays can retain an older shape, so consumers refresh authoritative GET rather than inferring archival intent or rewriting receipts.

Capture excludes inactive or archived named members; Call/Start rejects archived identity with `RESOURCE_MEMBER_ARCHIVED`. Busy named/anonymous protections or allocations reject archive or maintenance edits with `RESOURCE_IN_USE` and never release capacity. The member-specific future/retry guard rejects disable, rename or archive with `RESOURCE_MEMBER_WORKFLOW_IN_PROGRESS` when an already-started parent would otherwise be stranded; it checks the exact member, not unrelated resources in its pool. Explicit pre-start replacement remains audited through amendment.
