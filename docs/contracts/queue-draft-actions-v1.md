# Saved queue draft actions v1

API source review cleared. Local preview restarted after verified backup and quiet-write checks; browser acceptance pending.

All normal draft create/update/detail/list responses include `publishReadiness: {ready, blockReasons:[{code,message}], provisional:true}` and server-derived `allowedActions`. All versions 2/3/4 support the same actions. Inconsistent Drafts with publication-version linkage expose `PLAN_RECONCILIATION_REQUIRED` and no actions (the final coordinated local runtime update includes this guard). Only an unpublished Draft offers `edit` and `delete`; Publish is offered when current validation/admission reads pass. Incomplete drafts remain saveable.

Readiness reads the saved customer/selections, current catalog/duration/workflow configuration, maintenance, entitlement admission, active business/branch, Queue Day/intake, hours and waiting-intake threshold. It creates no ticket, allowance operation, reservation, allocation or workflow configuration. Resource occupancy is deliberately not a readiness blocker: publication can issue Waiting. Readiness is provisional; actual Publish repeats its authoritative transaction including allowance admission and may reject changed policy or depleted allowance. A read failure is a real error, never invented readiness.

`DELETE /vendor/tenant/:tenantSlug/queue/plans/:planId?location=:locationSlug` requires `Idempotency-Key` and JSON `{expectedPlanRevision:string}`. The same `tenant.queue.operate` permission and current branch assignment as draft save/publication apply; an assigned authorized staff member may delete another staff member's unpublished draft within that branch.

The authorized location-first transaction locks the draft, verifies Draft/no published ticket/no publication-version linkage and expected revision, then changes state to `discarded` and increments revision. No row/history is physically deleted. The complete before/after snapshots and authenticated actor/role are audited as `draft_delete`; the receipt is stored in the same transaction. Delete versus Publish or save has one winner under the same location/draft serialization.

Success is HTTP 200 `{deletedDraft:{id,planRevision,state:'discarded'}}`; exact-key replay returns the same tombstone result plus `replayed:true`, after current authorization. Changed payload/key reuse returns 409 `IDEMPOTENCY_CONFLICT`. A new key for an already deleted draft returns 410 `DRAFT_DELETED`. Stale revision returns 409 `STALE_REVISION`. Published or inconsistent linked drafts return 409 `PLAN_LOCKED`. Wrong tenant/branch or unknown ID remains 404 `INVALID_PLAN` without disclosing the other scope.

Deleted drafts are absent from normal lists. Normal detail, update and Publish return 410 `DRAFT_DELETED`. Historical create/update receipts are retained unchanged, but replay after deletion returns 410 instead of presenting the old editable draft. Historical create/update replay after publication returns 409 `PLAN_LOCKED` and requires an authoritative request refresh; the stored historical receipt remains unchanged. Delete receipt replay never recreates a row or a ticket. No published request, allowance or resource lifecycle is affected.

The frontend shares pending command/key ownership, uses a named destructive confirmation, retains the exact Delete body/key after an ambiguous response and removes cached draft/editor state only after an authoritative success/tombstone disposition. Cancellation sends no command. Existing unsaved-form and branch-bound review guards remain required.
