# Vendor dashboard full source and plan audit

Audited 13 October 2026 against fetched `origin/main` / `HEAD` `f7435a22`. Scope: all eleven existing dashboard sections, their nested tabs/forms/dialogs, shared account/auth flows, frontend API seams, corresponding vendor/billing/board authorization, and the agreed workflow/resource design. The original planning documents have been copied from the planning checkout into this branch without changing that checkout.

This is a source/contract and planning audit. It is not an authenticated browser walkthrough, penetration test, deployment certification, physical QR scan, or mobile application acceptance. New vendor-shell dependency/component work remains unconnected WIP and is excluded from claims about current main behavior. No product behavior is changed by this audit.

## Result and decision policy

The overall design remains sound, but the earlier plan was too coarse to serve as a complete migration acceptance contract. Fifteen gap groups below require explicit coverage or correction. These are planning gaps, not fifteen confirmed production defects.

Preserve existing behavior by default. Resolve ordinary layout/component choices during implementation. Do not silently change permissions, commercial policy, destructive outcomes or queue semantics to make the new layout easier. New workflow/resource behavior follows the already agreed foundation and its backend readiness gates. Runtime-owner input and meaningful evidence are required before any capability is represented as live.

The [preservation checklist](vendor-dashboard-rework-preservation-checklist.md) covers recent queue/board/quantity changes in detail. This document expands coverage to the entire dashboard. The [migration inventory](vendor-dashboard-migration-inventory.md) owns proposed destinations; the [UI rules](../design/vendor-ui-rules.md) own presentation standards.

## Authorization map to preserve

Source authority: `backend/src/services/permissions.js` plus action-specific handlers and current frontend guards. The backend remains authoritative; permission membership alone does not bypass assignment, self/owner restrictions, active membership, MFA, entitlement or commercial confirmation requirements.

| Action family | Current scope |
| --- | --- |

## Migration ordering and decisions still needed

1. **Shared shell:** role/capability/context/navigation/theme and route compatibility over today's ordinary queue. Implement useful fallback when only account/settings is permitted; preserve MFA-first behavior. Resolve route roots and tab URL mapping here, without needing another product interview for routine implementation choices.
2. **Operations:** live queue plus lifecycle tray/scanners; then bookings/check-in/payment responsibilities and clients/history. Prove ordinary operational parity before introducing future station/journey views.
3. **Administration:** locations/counters/services/availability/staff/settings/board, with explicit Resources relocation. Keep account/security reachable from either permitted workspace.
4. **Commercial/reporting/auth:** billing/capacity/credits, reports/ratings, shared login/vendor registration/onboarding/account presentation; do not expose unsupported template providers/features or alter customer flows through global CSS.
5. **Workflow/resource UI:** implement drafts/editor and capability-based setup against agreed contracts; no fake station IDs or operational allocation in the browser. Activate runtime only under its independent gate.
6. **Retirement:** remove old vendor primitives/styles after usage and compatibility checks; old monitor board access remains retired throughout.

The agreed visual target and one-seat workspace model need no new decision. Remaining material runtime/product gates are the already recorded workflow entitlement transition for booked-but-unadmitted work, pilot participants/quality targets, runtime station/resource readiness and evaluated AI publication. Template source rights remain relevant only if commercial source is reused; original reference-aligned implementation does not require buying it.

## Verification matrix for every affected slice

- Roles: owner, admin, assigned staff, unassigned/inactive membership, MFA-required and expired session; direct navigation as well as visible menus.
- Capability/plan: Free, active paid, exhausted usage, suspended/expired/wind-down where supported, disabled release capability; retain authorized resolution of current work.
- Context: multiple tenants/locations/counters, primary fallback, no active location, slug changes and async old-scope responses. Scope query keys and clear inaccessible cached/selected state.
- Data: loading, true empty, unavailable/error, validation, retry, long values, missing contact/media, partial paginated datasets and retained/frozen historical data.
- Mutations: confirmation cancellation, duplicate click, stale revision, concurrent actor, pending context/navigation, conflict reload and realtime reconnect; no accidental write during theme/workspace switching.
- Presentation: light/dark plus mobile/tablet/desktop and short heights, 44-pixel controls, tab/focus order, returned focus, screen-reader status/error labeling, scroll lock, safe-area/keyboard clearance, independently scrolling dialog body and fixed action footer.
- Security surfaces: camera unavailable/denied, manual entry, wrong/expired pairing, grant rotation/revocation, QR/code aspect ratio; proof/media safe access and no widened private projections.
- Shared surfaces: public vendor/join/ticket/booking paths, login/OAuth/payment/MFA returns, email/mobile links, customer account primitives and unauthenticated secure-board rendering.

Existing focused suites include frontend navigation/bootstrap, counter dispatch, queue lifecycle UI, board polling, duration units and booking check-in; backend counter dispatch/configuration, Queue Day time/repository/lifecycle/worker, board access/routes/cookies/projection/streams, service-duration limits, booking, staff access, notifications, account and billing/entitlement tests. Some source-contract tests assert old markup; update them to equivalent user-observable guarantees when extracting components. Do not use regex tests alone as interaction acceptance.

Authenticated runtime checks, a real camera/display pairing, direct mobile min/max proof, all-section visual walkthrough and workflow/resource activation remain **unverified by this audit**. Record the evidence for each before claiming the corresponding migrated feature accepted.
