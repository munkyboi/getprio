# Internal resource ledger foundation

## This slice

Additive backend foundation for resource-only location queues with one executable service item and one shared pool. `resourceLedger.executeCommand` owns a transaction, takes the scoped location lock first, and records a scoped command receipt and monotonically increasing ledger revision. Commands bind booking-item reservations, cancel protected reservations, allocate a called/confirmed ticket from its immutable known plan, and explicitly complete/terminate an allocation. Termination requires a reason. Scope IDs and actors are server-side inputs; this module has no API route, UI caller or production activation path.

Reservation bindings freeze pool/demand/revisions and interval. Allocation validates the captured plan against current configuration, converts an eligible booking reservation once, and creates actual occupancy atomically. Booking quantity does not multiply demand. A late booking start retains its protected reservation end; an implicit full-duration extension is not allowed. Duplicate command keys return their committed result; changed actor/action/payload with the same key conflicts. A failed command rolls back receipt, revision, binding and allocation together. A different-key repeat allocation returns a deterministic 409 before capacity or uniqueness errors, including after release. One ticket supports one allocation; another service session requires another work unit.

Actual unreleased allocations consume capacity even after expected end. The foundation conservatively blocks new protected intervals against existing occupancy for the whole interval, rather than assuming an expected end releases it. A future operational scheduling contract must explicitly address future reservations around active forecast ends; this conservative behavior is internal groundwork, not a newly exposed booking policy. Half-open protected intervals allow adjacency; competing transactions cannot exceed the scoped pool capacity when all use this interface.

Allocation records and command actors preserve audit outcomes. Account deletion anonymizes command actors through the existing reviewed reference policy; foreign keys also use SET NULL for actor deletion. Ledger scope/pool/ticket/booking-item foreign keys preserve tenant/location boundaries. An allocation can release only with completed or reasoned terminated outcome; neither cancellation nor forecast expiry releases it.

## Activation remains disabled

Existing `resource_pools_tracking_disabled_check` remains intact. New `resource_ledger_coverage_disabled_check` constrains writer coverage false. No historical data is backfilled, no occupancy is inferred from Called/service timing, and neither a ready snapshot nor an inference hook is added. The AI-owned snapshot consumer remains separate; proposal `resource-operational-snapshot-v1` is not produced by this module.

Current booking-create/reschedule/status/expiry paths and timing start/end paths are **not yet integrated** with this ledger. This slice supplies tested transaction primitives, not complete application writer coverage. Existing ordinary booking/queue behavior remains on its current paths. No caller may enable tracking by merely removing either constraint.

Before live use, integrate all booking writers under the same location-first lock, immutable binding lifecycle and domain authorization checks, plus activation reconciliation. Integrate service start/completion/interruption/extension with actual allocation commands in the same transaction as timing/booking outcomes; do not call this independent transaction wrapper from inside a prelocked booking/ticket transaction. Add a composable transaction-owned domain adapter when integration requires it, without exposing a way to bypass the lock. Validate call ordering/earliest-call constraints and all issuance channels. Reconcile pending payment holds and existing unmapped plans; implement coherent committed reads and producer completeness/watermarks. Only then consider lifting tracking/coverage constraints for explicitly authorized pilots.

Single-item v1 duration is an integer from 5 through 480 minutes, matching the vendor-service catalog and AI consumer contract. Fractional or longer quantity/composed durations fail closed; they need a separately reviewed extension. No condition/parallel/sequential multi-item execution, workflow journey, named-unit assignment, plan revision UI or public estimate change is included.

## Composable domain transaction prerequisite

`resourceLedger.withScopeTransaction({ pool, tenantId, locationId, actorUserId, authorize }, callback)` owns a fresh transaction and acquires the location lock before authorization or domain work. The mandatory authorizer receives the same client and frozen server-owned scope; it must recheck permissions and return exactly `true`. A denied actor cannot enter the domain callback or retrieve a retry receipt. The existing `executeCommand` remains an internal isolated-interface wrapper, not a route or authorization boundary.

The domain callback receives `(client, ledger)`. Use existing repositories with `{ client }` and await `ledger.executeCommand({ operationKey, command, payload })` sequentially. Commands use the enclosing immutable scope/actor and transaction; they cannot accept an arbitrary prelocked connection. For booking creation, insert the booking/items before reserving. For rescheduling, cancel the protected binding, update the item interval and reserve its replacement in that order. For start, allocate/convert and record the service observation together. For completion/interruption, update domain outcomes and explicitly release together. Any failure rolls back all domain writes, commands, receipts and revisions. A caught ledger error also aborts the transaction, preventing accidental partial reservation replacement. Concurrent or unfinished commands abort; pending work drains before the connection returns to the pool. Escaped ledger capabilities reject commands after the transaction closes.

These callbacks are trusted backend code. They must await every repository write, must not issue transaction-control SQL, and must not retain/reuse the raw client. Ledger receipts deduplicate **ledger commands only**; the enclosing domain callback still runs on a retry and must implement its own guarded/idempotent lifecycle transitions. Authorization is supplied by the domain adapter; the primitive does not infer membership or make an unscoped write safe. Actorless expiry jobs need a separately defined audited system-actor contract rather than an invented user ID.

This prerequisite does not reroute current application writers, implement booking status/payment policy, resolve existing lock inversions, add service extension or enable tracking. Production writer coverage remains incomplete and both disabled constraints remain intact. The next integration must move each participating domain transaction to this entry point before taking booking/ticket/pool locks, preserve current authorization and ordinary behavior, and reconcile historical state before a producer can report ready.

PostgreSQL regression coverage adds atomic cancellation, failed reservation replacement (including a caught conflict), failed booking conversion, completion/release rollback and commit, authorization under the location lock including replay denial, escaped/unfinished/concurrent command rejection, and a competing start waiting for a composed booking transaction. The fixture changes booking/ticket rows directly to prove atomicity; this is not end-to-end evidence for the current application endpoints.

Validation for this prerequisite: full backend suite 810 passed, seven unrelated opt-in skips, zero failures (817 total); the focused PostgreSQL interface passed all 24 cases. Backend typecheck, focused ESLint and diff whitespace checks passed. An initial full-suite run used the unrelated allowance test's default localhost port and failed to connect; rerunning with both test URLs explicitly targeting the disposable PostgreSQL container passed. Bitwarden remains unauthenticated, so no application environment/services or live database were used.

Review hardening: verify PostgreSQL's transaction-completion command tag is `COMMIT`. When a callback catches a raw-client SQL error, PostgreSQL can answer `ROLLBACK` to a subsequent COMMIT; the adapter rejects that result instead of acknowledging discarded writes. A real constraint-error regression proves allocation, receipt and revision rollback and successful subsequent connection reuse.
