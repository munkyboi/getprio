# Internal resource ledger foundation

## This slice

Additive backend foundation for resource-only location queues with one executable service item and one shared pool. `resourceLedger.executeCommand` owns a transaction, takes the scoped location lock first, and records a scoped command receipt and monotonically increasing ledger revision. Commands bind booking-item reservations, cancel protected reservations, allocate a called/confirmed ticket from its immutable known plan, and explicitly complete/terminate an allocation. Termination requires a reason. Scope IDs and actors are server-side inputs; this module has no API route, UI caller or production activation path.

Reservation bindings freeze pool/demand/revisions and interval. Allocation validates the captured plan against current configuration, converts an eligible booking reservation once, and creates actual occupancy atomically. Booking quantity does not multiply demand. Duplicate command keys return their committed result; changed actor/action/payload with the same key conflicts. A failed command rolls back receipt, revision, binding and allocation together. One ticket supports one allocation; another service session requires another work unit.

Actual unreleased allocations consume capacity even after expected end. The foundation conservatively blocks new protected intervals against existing occupancy for the whole interval, rather than assuming an expected end releases it. A future operational scheduling contract must explicitly address future reservations around active forecast ends; this conservative behavior is internal groundwork, not a newly exposed booking policy. Half-open protected intervals allow adjacency; competing transactions cannot exceed the scoped pool capacity when all use this interface.

Allocation records and command actors preserve audit outcomes. Account deletion anonymizes command actors through the existing reviewed reference policy; foreign keys also use SET NULL for actor deletion. Ledger scope/pool/ticket/booking-item foreign keys preserve tenant/location boundaries. An allocation can release only with completed or reasoned terminated outcome; neither cancellation nor forecast expiry releases it.

## Activation remains disabled

Existing `resource_pools_tracking_disabled_check` remains intact. New `resource_ledger_coverage_disabled_check` constrains writer coverage false. No historical data is backfilled, no occupancy is inferred from Called/service timing, and neither a ready snapshot nor an inference hook is added. The AI-owned snapshot consumer remains separate; proposal `resource-operational-snapshot-v1` is not produced by this module.

Current booking-create/reschedule/status/expiry paths and timing start/end paths are **not yet integrated** with this ledger. This slice supplies tested transaction primitives, not complete application writer coverage. Existing ordinary booking/queue behavior remains on its current paths. No caller may enable tracking by merely removing either constraint.

Before live use, integrate all booking writers under the same location-first lock, immutable binding lifecycle and domain authorization checks, plus activation reconciliation. Integrate service start/completion/interruption/extension with actual allocation commands in the same transaction as timing/booking outcomes; do not call this independent transaction wrapper from inside a prelocked booking/ticket transaction. Add a composable transaction-owned domain adapter when integration requires it, without exposing a way to bypass the lock. Validate call ordering/earliest-call constraints and all issuance channels. Reconcile pending payment holds and existing unmapped plans; implement coherent committed reads and producer completeness/watermarks. Only then consider lifting tracking/coverage constraints for explicitly authorized pilots.

No condition/parallel/sequential multi-item execution, workflow journey, named-unit assignment, plan revision UI or public estimate change is included.

## Verification

Disposable PostgreSQL 16 acceptance tests use `RESOURCE_LEDGER_TEST_DATABASE_URL` pointing to loopback database `getprio_ledger_test` (or the isolated CI service database `getprio_test`), creating/dropping only a random fixture schema. Local test runs skip the database interface cases unless this isolated target is explicitly configured. CI explicitly supplies its disposable PostgreSQL service URL so the transaction cases run in the hosted coverage gate. Application DATABASE_URL is never used for these tests.

Verified scenarios: five concurrent starts/four courts; same-key replay and changed-payload conflict; reservation conversion with no double count; concurrent reservation/start with one winner; overlapping/adjacent protected intervals; overdue occupancy until explicit termination; cancelled booking denial; cross-location scope/stale/unknown plans; scope/release/coverage SQL constraints and actor deletion. Focused lint and backend typecheck passed. The full backend suite and coverage command passed: 797 passed, 7 unrelated opt-in tests skipped, no failures (804 total). Aggregate local coverage was 61.9% statements/lines, 64.43% branches and 57.67% functions; this is not an 80% coverage claim. A fresh disposable PostgreSQL bootstrap passed init plus all 131 migrations, followed by schema verification. The first suite run exposed missing local dependency/default-port setup; locked dependencies and explicit isolated test targets resolved those failures before this successful run.

The ignored GetPrio application environment could not be restored because Bitwarden is unauthenticated. No GetPrio API services, live database or operator configuration were changed. The isolated database tests prove this interface's transactions; they do not prove integrated booking/session flows or a production allocation ledger.
