# Explicit service-session resource writer

This slice integrates the existing ticket service start, complete and interrupt actions with the location-first resource transaction. Current membership, ticket-state permission and staff branch or active-counter assignment are rechecked on the same client. The locked ticket must belong to the selected tenant/location. New starts require an active business/branch and service timing enabled; explicit completion/interruption can resolve existing service even after those settings are disabled.

An enabled resource scope or any historical booking reservation binding requires resource handling. Existing allocations always participate after tracking disable. Start validates the executable immutable plan through the ledger, checks current mapping/capacity and converts a compatible booking reservation once. Missing/stale protection or incomplete preexisting timing/allocation state rejects for reconciliation. Ordinary scopes without bindings/allocations keep their explicit timing behavior without allocating. Known draft resource metadata alone does not activate a disabled ordinary scope.

Allocation and ticket timing, event/webhook enqueue, command receipt and scope revision commit together. Completion explicitly releases with completed outcome; the existing staff interrupt action releases with terminated outcome and the server audit reason `Staff explicitly interrupted service.` This describes the selected action, not an inferred customer circumstance. Timing, queue outcome and linked booking completion stay in the same transaction. A failed event or booking write rolls all effects back. Existing postcommit notification/snapshot behavior remains.

Resource timing copies PostgreSQL allocation `started_at` and `released_at` directly in SQL, preserving timestamp precision. These are authoritative explicit service observations. Current single-item v1 has one work/session per ticket, with deterministic proposed producer references `ticket:<ticketId>` for work and `allocation:<allocationId>` for session/allocation. These references are documented for subsequent producer/capture integration, not emitted by this slice. Ordinary timing retains its explicit PostgreSQL clock observation without inventing an allocation/session ID.

Retries recheck current authorization and persisted outcomes; repeated start or identical finished outcome performs no new ledger/event write. Conflicting terminal outcomes reject. Calling and arrival never allocate. Queue closure, expected end and timing/configuration disable never release occupancy. A late booking keeps its protected end; no extension or second session on an existing ticket is introduced.

Production tracking and writer-coverage constraints remain disabled. Other payment/issuance writers, configuration and activation reconciliation, complete ready inventory/watermarks and capture/export integration remain outstanding. Snapshot v1, producer/inference/evaluation contracts and customer estimates are untouched. The producer remains fail closed.

Validation uses the actual ledger migration/adapter, explicit timing repository, permission rules and staff-assignment repository in disposable PostgreSQL with minimal ticket, event/webhook and booking fixtures. It covers four-court contention, exact persisted timestamps, protected conversion/end retention, tracking/configuration disable, retry/terminal races, overdue occupancy/queue closure, transaction rollback, access revocation while waiting for the location lock, unknown/stale plans, and ordinary/inconsistent state. This is integrated service transaction evidence, not authenticated live resource execution.
