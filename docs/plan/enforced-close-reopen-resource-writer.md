# Enforced manual close and reopen writer

Vendor manual close now calls `closeVendorQueueDay`; reopening uses the same location-first vendor Queue Day transaction as intake and deadline changes. The transaction rereads current actor, membership, permission, staff assignment/counter access, active tenant/branch and enforced mode, retaining accepted grants through commit. Close requires `tenant.queue.operate`; reopen requires `tenant.queue.reopen`, which belongs to owner/admin roles. Caller-supplied audit roles are replaced with the current locked membership role.

The branch uses the existing FK-compatible `FOR NO KEY UPDATE` boundary before tenant/user/membership and Queue Day locks. The transition, ticket outcomes, linked booking updates, segment history, warning obsolescence, lifecycle events, durable notification intents and one branch ledger revision commit or roll back together. Repeated close retains authorized idempotency without another revision; stale versions reject without changes. Concurrent reopening permits one transition. Its effective-hours predicate uses current database time after lock waits rather than transaction-start time.

Existing enforced close/reopen policy remains: waiting tickets receive carry-over offers, consumed carry-over tickets expire, called tickets become unserved and skipped tickets retain their status with terminal closure metadata. Only eligible nonterminal linked booking statuses change. Reopening clears closure metadata and opens intake, but does not restore prior ticket outcomes. Actual allocations and explicit service timing are retained; closing or reopening does not release occupancy or start a service.

Internal request reconciliation still uses the separate actor-free `closeQueueDay` entry point and shared locked closure implementation. No authorization exemption is chosen from a caller-supplied source string. These trusted system paths keep their prior boundary and remain outside coverage certification.

PostgreSQL tests reuse the existing Queue Day writer fixture and real lifecycle/event/outbox/ledger repositories and migrations. Coverage includes concurrent close/reopen, optimistic versions, both staff grant paths, owner/admin reopen permissions, current invalid access/activity/mode, tenant-first revocation with branch-FK insertion, post-write rollback including ticket/booking/segment effects, effective-hours expiry during contention, existing closure outcomes and occupancy retention, and actor-free reconciliation compatibility.

Validation: the disposable PostgreSQL full backend suite passed 1,055 tests with seven opt-in skips (1,062 total), with no failures. Focused source ESLint, backend typecheck and diff checks passed. Coverage was 67.73 percent lines/statements, 69.15 percent branches and 63.38 percent functions; no 80 percent threshold claim.

Manual enforced opening is covered separately in [Enforced opening](enforced-opening-resource-writer.md). Standalone system reconciliation revisions, terminal unused-protection cleanup, account deletion, catalog/settings writers and full activation reconciliation remain inventory gaps. Tracking and writer coverage remain constrained to false; the producer remains `not_ready`. No migration, UI, customer estimate, capture/export or inference change. Local and hosted checks do not establish authenticated live vendor resource execution.
