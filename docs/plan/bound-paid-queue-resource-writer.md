# Queue Day-bound paid queue issuance

Verified paid checkout fulfillment for an enforced Queue Day now locks its stored location before the payment row. The preliminary day read discovers scope only; payment tenant, Queue Day and provider checkout binding are reread and compared after the location lock. Current tenant, location, subscription, customer availability, accepting Queue Day/deadline and waiting threshold govern admission. Checkout payload slugs cannot redirect this bound writer. Authenticated customer availability holds a shared user-row lock through issuance so deletion/suspension updates serialize with ticket creation. Guest audit events retain the established null role; authenticated joins record Customer.

Tenant intake policy holds a shared row lock through issuance, so concurrent settings changes are observed before admission or wait for its commit. A duplicate durable billing receipt retries bound fulfillment when the payment remains unissued; terminal/issued outcomes retain duplicate safety. Payment sync resolves an already-issued bound ticket by location ID and supplies its current slug. Public payment-sync navigation consumes that slug so a branch rename does not strand the ticket.

Ticket insertion, scoped sequence, existing allowance consumption/email admission, ticket-created event/webhook, paid-to-ticket linkage and resource scope revision commit together. Duplicate successful callbacks reuse the issued ticket without another revision, event, push or allowance consumption. Notifications and snapshots run after commit against the bound location. Issuance does not allocate resources or invent a selected service plan.

Unavailable admission records the existing paid/refund-pending marker and releases the checkout allowance hold atomically; this does not execute a monetary refund. An overdue day reconciles closure before recording that marker. A savepoint discards attempted issuance when the deadline expires between initial admission and persistence, then commits current closure and the blocked paid outcome. Unexpected event, webhook, allowance or payment-link failures roll back the transaction. Repeated refund-pending callbacks remain terminal. Closure never releases actual occupancy or converted bindings; terminal protection cleanup remains a separate writer gap.

## Validation and boundaries

Real PostgreSQL tests exercise actual payment/ticket/persistence/ledger SQL with minimal transactional allowance, lifecycle, event/webhook, tenant/location and Queue Day lookup fixtures. Synthetic provider-paid input exercises the fulfillment adapter; it is not provider verification or a live payment. Coverage includes competing callbacks, current subscription/customer/branch admission, intake threshold, changed checkout/day binding while waiting for the location lock, atomic failure recovery, committed deadline reconciliation, retained occupancy and repeat safety. Full production bootstrap, allowance policy and authenticated live payment/resource execution are not claimed.
