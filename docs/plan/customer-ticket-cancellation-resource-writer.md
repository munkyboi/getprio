# Customer ticket cancellation resource writer

Public lookup-code cancellation of waiting and pending carry-over tickets now enters a dedicated location-first transaction. The route retains its existing ownership/status/location preflight and passes only the server-authenticated actor ID and the submitted contact fields to the service. The preflight is advisory: after acquiring the scoped location lock, the adapter rereads the current active user and locks the ticket by tenant, location and lookup code. It checks ownership and cancellable status again before domain writes.

The existing ownership rules remain: a ticket linked to a user requires that exact account owner; an unclaimed ticket accepts the current authenticated user's matching contact or the request's matching email/phone. A contact payload cannot override a linked account owner. A missing, deletion-requested or platform-suspended authenticated actor rejects. A ticket claimed, changed or called while cancellation waits for the location lock is checked in its resulting state. Closing or deactivating a branch does not prevent an owner from cancelling an otherwise waiting/carry-over ticket. No OTP or stronger guest-identity guarantee is introduced by this slice.

Cancellation, linked booking outcome, unused protection cleanup, queue segment, event/webhook, ledger receipts and scope revision commit together. The linked bookings are locked in ID order and independently checked against the same customer identity/contact rules using their customer account/contact fields. An inconsistent booking owner rejects and rolls the ticket cancellation back. Active pending/confirmed/rescheduled linked bookings use the existing ticket-cancelled fulfillment policy; terminal booking statuses stay unchanged. Vendor cancellation still requires `tenant.booking.manage` for active linked bookings. Existing allocations or unfinished explicit timing reject customer cancellation; converted bindings also reject. Cancellation never releases occupancy. Frozen protected bindings are cancelled even after draft edits or tracking disable.

`resourceLedger.withCustomerTicketCancellationTransaction` is a trusted internal adapter boundary with a mandatory authorizer. Its guest actor is null rather than an invented user. Its ledger capability accepts only `cancelReservation` with `ticket:<ticketId>:reservation:<reservationId>:customer-cancel`, verifies the payload/key, and requires that reservation's booking be linked to the scoped lookup-code ticket already cancelled with a customer/carry-over reason in this transaction. It cannot reserve, allocate, release or use system-expiry keys, for guests or authenticated customers. Existing vendor and system-expiry boundaries keep their separate restrictions. Receipts retain the real actor ID or null guest actor; no contact proof is persisted in the ledger.

Duplicate requests serialize at the location lock: one cancellation succeeds, subsequent requests reject the now-terminal ticket without another event, protection command or revision. Postcommit queue notifications/snapshot behavior remains unchanged. Cancellation does not need an open Queue Day and does not infer an actual service observation. The HTTP response shape and public/versioned route mount remain unchanged.

Validation uses actual PostgreSQL ledger/timing/assignment repositories with minimal transactional ticket, booking, event/webhook and segment fixtures. It verifies guest cancellation after tracking disable, account-owner restrictions, carry-over cancellation and terminal-booking preservation, concurrent requests, event/webhook rollback, changed ownership/status/current-user access during lock contention, wrong scope/inconsistent booking owner, and retained actual occupancy. Capability regressions reject other commands, unrelated ticket protection, pre-cancellation cleanup and expiry keys. Existing HTTP route tests verify request DTOs cannot inject an actor or vendor ticket ID; those route tests mock the queue service. These checks do not claim full production-schema or authenticated live cancellation proof.

Tracking and writer-coverage constraints stay disabled. Issuance/payment, operational state changes, Queue Day closure/carry-over expiry, account-deletion cancellation, configuration/reconciliation and complete ready inventory remain separate writer gaps. No producer/snapshot/capture/export/inference contract, readiness or customer-estimate change is made.

Local verification: the focused PostgreSQL/HTTP/ledger command passed 79 tests. The final full backend coverage command using the dedicated disposable PostgreSQL target passed 916 tests with seven unrelated opt-in skips (923 total), with no failures. Focused ESLint, backend typecheck and diff check passed. Aggregate coverage is about 63 percent, not an 80 percent coverage claim. No application services or live database mutations were run.
