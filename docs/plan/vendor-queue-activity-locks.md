# Vendor queue activity locking

New explicit service starts and the common open-vendor-queue adapter now opt into a tenant share lock in the common vendor transaction authorization phase, before reading/locking user and membership grants. The order is location, tenant, then actor/access grants, matching staff access changes at the tenant/membership boundary. Activity is still checked in the action callback against the held tenant row. The existing location-first transaction already holds the branch row; the accepted tenant activity row is now held too, through commit or rollback. This covers service start, vendor walk-in issuance, calling, barcode confirmation and skipped restoration. Concurrent tenant deactivation waits for accepted work to commit. If deactivation holds the tenant row first, the operation waits and rereads the committed inactive value before rejecting. An inactive result rolls back all requested action writes, including any newly inserted scope.

Actor, membership and accepted staff assignment/counter grants remain locked by the common vendor adapter. Action permissions and admission/lifecycle checks keep their existing policy. Shared tenant locks are compatible with other shared tenant locks; this does not add a tenant-wide exclusive lock across branches. Tenant row updates may wait while accepted operations finish. Other writer lock orders still require their own audit; database transaction errors follow the existing rollback path.

Tenant activity remains a new-work gate. Completion and interruption do not take this tenant share lock, and authorized staff can explicitly release actual occupancy after tenant/branch or timing disable, including while a tenant flag update is still uncommitted. Calling, confirmation, admission and restoration do not allocate or release resources. No reservation, receipt, resource capability or existing terminal-outcome policy changes.

This closes the tenant-activity check-to-commit gap for these specific vendor paths, not the complete writer inventory. Enforced/system lifecycle, deletion cancellation, configuration/reconciliation and complete readiness prerequisites remain separate. Tracking/coverage gates stay disabled; producer remains `not_ready`. No activation, backfill, capture/export/inference or customer estimate changes.

Validation uses actual ledger, authorization, assignment, timing and operational ticket code with minimal transactional event/lifecycle/allowance fixtures. PostgreSQL barriers cover each affected action, accepted work blocking actual deactivation until commit, deactivation-first lock-wait reread/denial, the actual staff-access transaction wrapper against each action in both commit orderings, event-failure rollback/unlock, simultaneous service starts at distinct branches, and explicit completion/interruption finishing while a tenant activity update is uncommitted. Local database proof does not establish authenticated live queue execution or full production-schema lifecycle behavior.

Final disposable local PostgreSQL 16.14 backend suite after the lock-order regression: 998 passed, seven opt-in skips (1005 total), zero failures. Focused ESLint, backend typecheck and diff checks passed. Coverage: 66.13 percent lines/statements, 69.27 percent branches, 61.52 percent functions; no 80 percent threshold claim. The initial Docker runtime encountered I/O failures; this successful final run used an isolated localhost database outside Docker.
