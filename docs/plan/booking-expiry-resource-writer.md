# Automatic pending-booking expiry

Lazy expiry entry points now enumerate eligible tenant/location scopes, then update bookings under the same location-first transaction as resource reservation cancellation. They reapply the caller's tenant/location/customer filters and one captured server cutoff inside each transaction. Expiry applies only to pending bookings with an elapsed expiry timestamp, no payment proof, no check-in and no linked queue ticket. The discovery read does not authorize or mutate a booking; locked SQL rechecks eligibility.

Booking status, expiry timestamp/reason, protected reservation cancellation, command receipts and scope revision commit together per location. A failure rolls back that location, including all its expired bookings. Different locations are separate transactions. Notifications are attempted after each location commit; durable notification delivery and global batch atomicity are not introduced.

The internal `withSystemExpiryTransaction` boundary uses a null actor rather than impersonating a customer, including bookings retained after account deletion. It is never built from a request DTO and exposes only expiry-keyed reservation cancellation. Command validation binds the operation key's booking/reservation IDs to the payload and persisted scope; the booking must already be canceled with an elapsed explicit expiry, no proof and no arrival. Reserve, allocate, release and cancellation of an unexpired booking are denied, and even caught command failures poison the transaction. Normal user transactions still require canonical user identity and explicit authorization. Existing nullable command actor schema is reused; no new migration or system user is created.

Frozen bindings survive configuration edits and tracking disable. Converted bindings fail closed without releasing occupancy. Competing expiry scans recheck state after acquiring the location lock; proof committed while the scan waits prevents expiry. Direct unscoped repository expiry is rejected. Candidate lookup is read-only and carries caller filters; large identifiers are passed without Number conversion in this path.

Production tracking and writer coverage remain disabled. Check-in, explicit service start/allocation and completion/termination release, other payment writers, configuration/reconciliation and ready snapshot inventory remain outstanding. No activation/backfill, live inference hook, snapshot v1 interface or customer estimate changes.

Tests use the real expiry repository, ledger adapter/migration and disposable PostgreSQL with minimal booking fixtures. Coverage includes deleted-customer identity, ordinary bookings, immutable protection, competing scans, customer isolation, proof/arrival/status/deadline exclusions, proof while waiting for the lock, SQL failure rollback, converted occupancy, restricted system commands and unchanged user-actor validation. Live authenticated resource execution is not claimed.
