# Vendor call and confirmation resource writer

Vendor call-next and barcode confirmation now enter the shared location-first current-actor transaction. Call-next rechecks `tenant.queue.operate`; confirmation rechecks `tenant.ticket.update_state`. Existing service/outcome/cancellation callers keep the ticket-operation default. Active membership/user and staff branch or active-counter assignment are reread on the same transaction client before domain work. Permissions are selected by trusted backend adapters, not request fields.

The open-queue adapter rereads the current branch/tenant active flags, lifecycle mode and timezone under the location lock. It checks the Queue Day there and derives the scoped date from the authoritative business date or current timezone. Legacy closure checks use that same scoped timezone date. Overdue enforced-day reconciliation commits its existing closure/outbox and scope revision before rejecting the requested action; other failures roll back. This does not complete the separate closure writer's protection-cleanup coverage. Actual unreleased occupancy remains occupied.

Call-next rechecks any supplied counter's exact, safe ID, active state and tenant/location scope; the optional no-counter path remains supported. It locks the current called ticket and preserves the existing one-called-ticket-per-location/date policy. Competing calls serialize, so a second caller sees the committed called ticket instead of independently selecting another waiting ticket. The existing repository priority and scheduled-start guard select the next eligible waiting ticket. Arrived bookings scheduled in the future remain waiting while eligible ordinary tickets can still be selected. Calling commits the ticket status, event/webhook, optional existing prediction observation and scope revision together. It does not allocate, convert protection or start service timing.

Booking call eligibility uses `clock_timestamp()` rather than PostgreSQL transaction-start `NOW()`. A transaction that starts and then waits for the location lock can therefore recognize a booking that becomes ready during the wait. Call/confirmation timestamps also use the current database clock rather than recording a time before the lock was acquired. These remain call/confirmation observations, never inferred actual service starts. Existing prediction sampling continues; no producer/capture/inference contract changes.

Confirmation locks the current called ticket and checks the scanned lookup code before writing. A fresh confirmation commits its timestamp, event/webhook and scope revision together. Concurrent/repeated confirmation retains the exact persisted timestamp and produces no duplicate event, webhook, revision advance or customer push. The response still includes the ticket/snapshot. Neither calling nor confirming releases actual occupancy. Postcommit notification/snapshot hooks remain outside the transaction.

The delayed Sonar finding from #340 (`javascript:S3776`, command function complexity 19 above the 15 limit) is addressed by extracting customer-cancellation binding and system-expiry binding validation into separate named helpers. SQL eligibility, command/key restrictions, receipt fingerprints and transaction semantics remain unchanged; existing actual PostgreSQL negative-boundary tests rerun. Historical #340 analysis is distinct from analysis of this follow-up head.

Validation uses the actual ticket repository for current-called lookup, waiting selection, call and confirmation, plus actual ledger/timing/assignment repositories. The PostgreSQL schema is a minimal contract fixture, not a full production bootstrap; events/webhooks and request-time lifecycle writes remain minimal transactional fixtures. Regressions cover competing calls, wrong barcode and concurrent confirmation, early booking versus eligible ordinary work, eligibility/call time after lock contention, event/webhook rollback, current staff access and counter/branch scope, and current enforced mode/committed overdue reconciliation with retained occupancy. Existing customer and service-session regressions rerun. The full backend coverage command passed 923 tests/seven unrelated opt-in skips (930 total); focused ESLint, backend typecheck and diff check passed. Aggregate coverage is about 63 percent, not an 80 percent claim. No authenticated live operation proof is claimed.

Tracking and writer coverage remain disabled. Restoration, issuance/payment, manual/system closure/carry-over expiry, account-deletion cancellation, configuration/reconciliation and complete ready inventory remain separate gaps. This does not implement parallel multi-court calling, multistage routing, activation or a ready producer.
