# Customer booking resource writers

## Initial scoped creation slice

Customer creation now enters resourceLedger.withScopeTransaction before taking any booking/item/allowance locks. Its authorizer rechecks the authenticated actor still exists and has not requested deletion, and rechecks the public approved tenant and active location with matching canonical scope. The existing route authentication, contact verification, pricing and allowance policies remain in effect.

Inside the location lock, current catalog/location service rules and availability are reloaded on the same client. Changed item prices, intervals, names or payment requirements reject instead of silently changing the selected booking. Overlapping booking counts and store-hour fallback also use that transaction client. Capacity is rechecked immediately before inserting the booking and bundle items. Creation, allowance consumption and location ledger revision advance commit together; failure rolls everything back and emits no post-commit intake notification.

The first creation slice serializes competing customer creates. That initial slice did not serialize every capacity writer: vendor reschedule/status, proof/payment transitions, cancel/no-show/expiry, check-in, queue issuance/session completion and configuration still need their own coverage. The first creation slice did not create a frozen resource reservation; resource mappings remain draft and tracking disabled. Ordinary composed booking/quantity behavior stays supported while single-item resource execution remains a later, separately gated runtime. No allocation, timing inference, snapshot-ready producer or prediction hook is added. Writer coverage remains false; a successful creation does not certify full coverage or activation.

Revision advance belongs to this covered creation transaction. This is not whole-request idempotency: existing OTP/request retry semantics remain, and future lifecycle integration must define guarded retries. Existing unintegrated writes can still race with creation, so do not generalize the create-versus-create capacity guarantee to reschedules or status changes.

Real PostgreSQL tests execute the production booking service and scoped adapter against minimal transactional repository fixtures: last-slot simultaneous creates yield one booking/item/allowance/revision; allowance failure rolls back all writes; deletion-requested actor and changed tenant/location gates deny; changed catalog/availability rejects. These fixtures prove transaction boundaries, not full deployed endpoint or production-schema migration behavior. Existing unit and customer route tests retain their availability, bundle and notification coverage.

Validation: full backend suite 817 passed, seven unrelated opt-in skips, zero failures (824 total); backend typecheck, focused ESLint and diff checks passed. The first full run exposed two customer route fixtures still mocking the old transaction wrapper; those fixtures now exercise the scoped authorizer callback. No application environment/services or live database were used.

Sonar follow-up: shared the duplicated customer route transaction fixture and replaced awaited catalog lookup loops with bounded all-settled reads. Every sibling read completes before a failure returns to the enclosing transaction; a focused deferred-read regression checks that behavior. Full backend suite after this change: 818 passed, seven unrelated opt-in skips, zero failures; lint/typecheck/diff checks passed.


## Gated reservation creation and customer cancellation

The follow-up adapter creates an immutable protected reservation for a persisted booking item only when its mapped pool has tracking enabled. Disabled draft configuration creates no reservation or ledger receipt and retains ordinary quantity/composed booking behavior. Unmapped services retain ordinary booking behavior. A booking containing an enabled resource item must have exactly one item, quantity one and an integer interval of 5–480 minutes. Demand is taken from the scoped service requirement, never multiplied from customer quantity. The existing ledger command freezes item identity, pool/requirement revisions, units and interval, checks protected reservations and unreleased occupancy, and inserts its receipt in the same transaction as creation and allowance consumption. Conflict rolls back all of those writes.

Customer cancellation now enters the location-first scoped adapter, checks the undeleted authenticated actor, locks and reloads the booking, then rechecks ownership, tenant/location scope, arrival and cancellable status. The guarded status update, cancellation of existing protected bindings and ledger revision advance commit together. Bindings are selected by immutable booking/scope identity even if pool tracking or demand has changed. Converted bindings reject cancellation and actual allocations are never released here. Notifications run after commit. Concurrent duplicate cancellation has one successful commit and notification; the second request receives the existing state conflict rather than whole-request receipt replay.

Production tracking and coverage constraints remain unchanged and false. Tests enable tracking only in an isolated fixture schema to exercise the gated path. This does not authorize activation, backfill, a ready snapshot, inference hooks or customer estimate changes. Vendor cancellation/status/reschedule, proof/payment transitions, no-show/expiry, check-in, session allocation/release and configuration/reconciliation remain explicit coverage gaps. Revision may advance more than once when a domain write also issues a ledger command; it is a monotonic invalidation value, not a booking count.

The PostgreSQL fixture now applies the actual ledger migration atop minimal application tables. It exercises simultaneous resource overflow independently of ordinary capacity, immutable demand after edits, disabled quantity behavior, unsupported quantity/composition/duration rollback, cancellation rollback on SQL failure, converted occupancy protection, actor/ownership checks, duplicate cancellation and arrival while cancellation waits for the location lock. Application repositories remain transactional fixtures; this is not evidence of a live authenticated resource booking or full writer coverage.

Follow-up validation: 838 backend tests passed, seven unrelated opt-in skips, zero failures (845 total). Backend typecheck, focused ESLint and diff checks passed. Tracking was enabled only in the disposable PostgreSQL fixture; no application environment, live database or inference interface was changed.
