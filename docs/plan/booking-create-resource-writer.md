# Customer booking creation: first scoped writer

Customer creation now enters resourceLedger.withScopeTransaction before taking any booking/item/allowance locks. Its authorizer rechecks the authenticated actor still exists and has not requested deletion, and rechecks the public approved tenant and active location with matching canonical scope. The existing route authentication, contact verification, pricing and allowance policies remain in effect.

Inside the location lock, current catalog/location service rules and availability are reloaded on the same client. Changed item prices, intervals, names or payment requirements reject instead of silently changing the selected booking. Overlapping booking counts and store-hour fallback also use that transaction client. Capacity is rechecked immediately before inserting the booking and bundle items. Creation, allowance consumption and location ledger revision advance commit together; failure rolls everything back and emits no post-commit intake notification.

This serializes competing customer creates. It does not yet serialize every capacity writer: vendor reschedule/status, proof/payment transitions, cancel/no-show/expiry, check-in, queue issuance/session completion and configuration still need their own coverage. No frozen resource reservation is created by this slice; resource mappings remain draft and tracking disabled. Ordinary composed booking/quantity behavior stays supported while single-item resource execution remains a later, separately gated runtime. No allocation, timing inference, snapshot-ready producer or prediction hook is added. Writer coverage remains false; a successful creation does not certify full coverage or activation.

Revision advance belongs to this covered creation transaction. This is not whole-request idempotency: existing OTP/request retry semantics remain, and future lifecycle integration must define guarded retries. Existing unintegrated writes can still race with creation, so do not generalize the create-versus-create capacity guarantee to reschedules or status changes.

Real PostgreSQL tests execute the production booking service and scoped adapter against minimal transactional repository fixtures: last-slot simultaneous creates yield one booking/item/allowance/revision; allowance failure rolls back all writes; deletion-requested actor and changed tenant/location gates deny; changed catalog/availability rejects. These fixtures prove transaction boundaries, not full deployed endpoint or production-schema migration behavior. Existing unit and customer route tests retain their availability, bundle and notification coverage.

Validation: full backend suite 817 passed, seven unrelated opt-in skips, zero failures (824 total); backend typecheck, focused ESLint and diff checks passed. The first full run exposed two customer route fixtures still mocking the old transaction wrapper; those fixtures now exercise the scoped authorizer callback. No application environment/services or live database were used.
