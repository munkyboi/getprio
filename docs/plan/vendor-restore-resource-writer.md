# Vendor skipped-ticket restoration resource writer

Restoration now uses the shared location-first current-actor transaction with `tenant.ticket.update_state`. Current active user/membership, staff branch or active counter assignment, branch/business active flags, lifecycle mode and timezone are reread before mutation. The target uses the actual tenant/location-scoped ticket `FOR UPDATE` lookup and safe positive integer ID validation. Barcode mismatch stays hidden as not found.

A skipped ticket can return to waiting only during its same open and accepting Queue Day. Date scope, enforced current Queue Day identity, terminal timestamp, skipped status and recovery metadata are checked under the lock. Recovery before the existing deadline retains the recovery band; after the deadline it rejoins the normal band. The authoritative enforced business date supplies the scope when no trusted date is specified. Current database auto-pause settings and waiting inventory are checked in the same transaction, so competing restorations cannot both claim the last waiting place. This waiting threshold is distinct from resource capacity. Public/paid issuance remains a separate writer gap.

Any allocation history, explicit timing history, or converted reservation binding rejects restoration even after tracking is disabled. Converted bindings are found through the booking's queue ticket or frozen booking service plan. Restoration neither allocates nor releases occupancy; unused booking protection and the frozen plan remain unchanged. Normal ordinary tickets continue to use the existing recovery behavior.

The ticket update, recovery-band change, call/confirmation clearing, event/webhook and scope revision commit together. Repeated/concurrent requests have one success; a loser sees the committed waiting state and receives a conflict. Event/webhook failure rolls everything back. Restoration timestamps use the current database clock after lock acquisition. The shared adapter preserves committed overdue closure/outbox/revision before rejecting restoration; this does not complete closure's separate protection-cleanup coverage. Postcommit notification, auto-pause and snapshot hooks remain outside the transaction.

Validation uses actual PostgreSQL ticket lookup/restoration/waiting SQL and ledger/timing/assignment repositories. The intake check uses the production lifecycle service with a fixture Queue Day lookup. Schema, lifecycle reconciliation, events/webhooks and postcommit snapshot/automation are minimal fixtures, not a full production bootstrap or authenticated live workflow. Regressions cover competing requests and the final waiting place, protection/plan preservation, expired recovery deadline including location-lock contention, ordinary restoration, barcode/scope/unsafe ID/current access, current enforced accepting day, old or terminal days, historical/active allocations and converted bindings, transactional rollback and overdue commit/retry safety.

The full backend coverage command passed 929 tests with seven unrelated opt-in skips (936 total). Focused ESLint, backend typecheck and diff check passed. Aggregate coverage remains below 80 percent; no threshold-compliance claim.

Tracking and writer coverage stay disabled; the producer remains `not_ready`. No parallel calling, multistage routing, activation/backfill, ready inventory, customer estimate or AI capture/inference contract changes. Issuance/payment, closure/carry-over expiry, account deletion, configuration/reconciliation and complete ready inventory remain separate gaps.
