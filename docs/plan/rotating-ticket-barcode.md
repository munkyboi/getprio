# Two-minute arrival barcode

Production customer API: authenticated GET `/api/v1/account/queue/tickets/{ticketId}/barcode` returns `{ barcodeToken, issuedAt, expiresAt, serverNow }`, with UTC ISO timestamps and `Cache-Control: no-store`. Barcode values are `QB` followed by 32 uppercase hexadecimal characters, suitable for Code128. Repeated requests within validity return the same value; renewal occurs at expiry with a fresh nonce. Database time supplies the exact 120-second lifetime. Signing uses the existing JWT secret with domain-separated HMAC input containing exact ticket, tenant, branch, owner and nonce; an unavailable signing key rolls issuance back.

The endpoint requires exact persisted ownership and current account eligibility. Unknown, non-owner or developer/Sandbox tickets return 404. Eligible statuses are waiting, called, skipped and pending_carry_over, with no arrival confirmation, service start/end/outcome or terminal timestamp. Other lifecycle states return 409 TICKET_BARCODE_UNAVAILABLE. Rate limiting applies to authenticated users. Barcode requests cannot change ticket IDs, lookup codes, status or service timing.

First successful issuance enrolls the ticket in persisted rotating protection. Enrollment remains after expiry or confirmation, preventing a static-code bypass. The ordinary scanner endpoint accepts `{ barcodeToken }` for rotating values and retains `{ lookupCode }` for un-enrolled tickets. Under its existing location and current-called-ticket locks, confirmation checks expiry, lifecycle, scope and HMAC before changing arrival confirmation. Wrong, expired, superseded or replayed values fail closed. Confirmation does not start service. Issuance takes the same location-before-ticket locks, so an enrollment racing static confirmation cannot permit both. Guests and other un-enrolled tickets retain the ordinary flow; an enrolled ticket's fixed web reference is no longer a valid arrival credential.

Migration adds `queue_ticket_barcodes` with a ticket deletion cascade and an exact duration check; bootstrap cleanup and release schema verification cover the table and constraints. No resource tracking or inference activation changes.

Coordinated mobile implementation: commit c7957a5 in codex/mobile-booking-lists-ui implements this contract with shared card/modal token state, server-relative countdown, expiry/background invalidation, no static fallback for eligible tickets, and polling during modal display. The mobile thread reports 349 tests, clean analysis, signed build and install/launch on both devices; these are mobile-thread evidence, not live API or scanner proof. Merge, deployment and physical end-to-end scanning remain separate gates.
