# Vendor service deactivation writer

The vendor service DELETE route passes the authenticated actor and server-resolved tenant to a tenant catalog transaction. Deactivation retains the existing service record and returns the ordinary formatted service response. Assigned staff, revoked memberships, deleted/suspended actors and foreign tenants are denied by current grants held through commit. Inactive vendor and branch administration remains supported. No new booking entitlement or activation policy is added.

A tenant-wide service affects every existing branch. The boundary locks all tenant branches in numeric database ID order with FOR NO KEY UPDATE, then the tenant with FOR UPDATE, then current user/membership grants, then the current tenant-owned service with FOR UPDATE. Branch locks are compatible with tenant-first grant mutations performing branch foreign-key checks. The tenant lock blocks new branch inserts through their existing tenant foreign key. A branch committed while the catalog writer was waiting for its tenant lock causes a 409 reload conflict before domain writes. Vendors without branches can deactivate services without creating resource scope state. No ledger command capability is exposed. Service lookup and update retain exact PostgreSQL identifiers, including values above the JavaScript safe-integer range.

An active service becoming inactive and one revision per existing branch commit atomically. Existing scope revisions advance once; absent scopes are initialized and advanced. Concurrent/repeated deletion of an already inactive service returns the current service without another domain mutation or revision. Missing or renamed services return the existing 404 contract. Failure after service update or final revision writes rolls the entire transaction back.

Existing bookings and bundle items, protected reservations, actual allocations, immutable ticket service plans, explicit service timing, location service settings and resource requirements remain intact. Deactivation does not cancel admitted work or infer a release. Availability branch moves reuse the same ordered bulk revision helper without changing their save semantics.

Disposable PostgreSQL coverage uses real service/location/availability repositories and the actual ledger migration. The fixture includes the production branch-to-tenant foreign key. Tests cover current access, stale grants/service identity after contention, branch insertion before and during the tenant lock, held locks, competing deactivations, rollback after final revisions, numeric branch move compatibility, no-branch vendors, inactive administration and preservation of existing protection/occupancy/timing. HTTP and handler coverage verifies staff denial, authenticated actor forwarding and response shape. Live authenticated vendor service-form execution remains unverified.

Catalog create/edit and location-service saves, branch creation/default hours and settings, protection cleanup and activation reconciliation remain inventory gaps. Resource tracking and writer coverage remain disabled; the operational producer stays not_ready. No migration, dashboard/mobile UI, estimates, inference or capture/export contracts change.

Local validation: full isolated PostgreSQL backend coverage passed 1,139 tests with seven opt-in skips (1,146 total), zero failures. The initial focused PostgreSQL/HTTP/handler suite passed 172 tests before the final tenant-first revocation and exact-identifier cases. Changed-source ESLint, backend typecheck and diff checks passed. Aggregate coverage is 68.56 percent lines/statements, 70.55 percent branches and 67.16 percent functions; this is not an 80 percent coverage claim.
