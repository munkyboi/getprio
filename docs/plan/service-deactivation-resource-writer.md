# Vendor service editing and deactivation writer

The vendor service PATCH and DELETE routes pass the authenticated actor and server-resolved tenant to a tenant catalog transaction. PATCH includes the dashboard Active toggle, reactivation, ordinary metadata edits and accompanying location-service mappings. Payloads normalize against the locked current service, and tenant location resolution and mapping upserts use the transaction client. The existing booking admission policy is checked on that client for PATCH. Deactivation retains the existing service record and returns the ordinary formatted service response. Assigned staff, revoked memberships, deleted/suspended actors and foreign tenants are denied by current grants held through commit. Inactive vendor and branch administration remains supported. No new booking entitlement or activation policy is added.

A tenant-wide service affects every existing branch. The boundary locks all tenant branches in numeric database ID order with FOR NO KEY UPDATE, then the tenant with FOR UPDATE, then current user/membership grants, then the current tenant-owned service with FOR UPDATE. Branch locks are compatible with tenant-first grant mutations performing branch foreign-key checks. The tenant lock blocks new branch inserts through their existing tenant foreign key. A branch committed while the catalog writer was waiting for its tenant lock causes a 409 reload conflict before domain writes. Vendors without branches can deactivate services without creating resource scope state. No ledger command capability is exposed. Service lookup and update retain exact PostgreSQL identifiers, including values above the JavaScript safe-integer range.

An active service becoming inactive and one revision per existing branch commit atomically. Existing scope revisions advance once; absent scopes are initialized and advanced. Concurrent/repeated deletion of an already inactive service returns the current service without another domain mutation or revision. Ordinary successful PATCH saves preserve their existing write semantics and advance every branch once per save; concurrent partial edits use current locked metadata and preserve independent changes. Missing or renamed services return the existing 404 contract. Failure after service update or final revision writes rolls the entire transaction back.

Existing bookings and bundle items, protected reservations, actual allocations, immutable ticket service plans, explicit service timing, resource requirements and location service settings omitted from PATCH remain intact. Explicit PATCH mappings retain the ordinary capacity/activity/price update behavior and commit together with service edits and revisions. Deactivation does not cancel admitted work or infer a release. Availability branch moves reuse the same ordered bulk revision helper without changing their save semantics.

Disposable PostgreSQL coverage uses real service/location/availability repositories and the actual ledger migration. The fixture includes the production branch-to-tenant foreign key. Tests cover current access, stale grants/service identity after contention, branch insertion before and during the tenant lock, held locks, competing deactivations, rollback after final revisions, numeric branch move compatibility, no-branch vendors, inactive administration and preservation of existing protection/occupancy/timing. HTTP and handler coverage verifies staff denial, authenticated actor forwarding and response shape. Live authenticated vendor service-form execution remains unverified.

Catalog creation and other internal catalog callers, branch creation/default hours and settings, protection cleanup and resource activation reconciliation remain inventory gaps. Resource tracking and writer coverage remain disabled; the operational producer stays not_ready. No migration, dashboard/mobile UI, estimates, inference or capture/export contracts change.

All service PATCH writes now share the current-authorized catalog boundary, including metadata and mapping edits; no active-to-inactive transition through the vendor service routes bypasses branch revisions. Tenant location lookup and mapping writes also preserve exact PostgreSQL identifiers.
