# Account-deletion resource writer proposal

Status: documentation-only proposal. Source baseline: main `20089c66b776f8ff4bfb919ab193de2e726112f5`. No implementation, migration, cleanup run, resource activation or writer-coverage certification is supplied by this document. It narrows the account-deletion gap in the [coverage checkpoint](resource-writer-coverage-status.md); that checkpoint remains historical.

## Current request and separate cleanup

The authenticated [account route](../../backend/src/routes/accountRoutes.js) accepts only the caller's identity, retains its feature gate and rate limit, passes the trusted session, clears the browser session after success and returns HTTP 202. The [request service](../../backend/src/services/accountDeletionService.js) locks the user first, verifies the current password or recent supported provider authentication, then commits the deletion receipt, account flag, session revocation and notification suppression together.

The request immediately removes the customer inbox and browser push subscriptions, disables mobile registrations, disables notification channels on **all** owned tickets and bookings, obsoletes pending/retry/processing notification outbox entries and removes vendor reviews. It cancels only `waiting` and `pending_carry_over` tickets, closes their open segments and records cancellation events. It waits for locked tickets and rechecks status; it does not use `SKIP LOCKED`. Called or in-service work is not cancelled. Booking notification suppression does not change booking lifecycle status. Queue refresh runs after commit; its failure must not undo the receipt.

These writes currently have no branch resource revision or unused-protection reconciliation. The user-first order creates a source-derived compatibility concern with branch-first resource writers; this audit has not reproduced a deadlock. Existing [integration tests](../../backend/tests/accountDeletion.integration.test.cjs) cover authentication, retries, waiting-ticket cancellation, concurrent call-next and rollback, but do not certify resource integration.

The later [worker](../../backend/src/services/accountDeletionWorker.js), [inventory](../../backend/src/services/accountDeletionInventoryService.js) and [reviewed anonymization](../../backend/src/services/accountDeletionAnonymizationService.js) remain separate writers. Actor references, foreign keys and cascades require their own operational-effect inventory. Accepting a request does not prove erasure, retention completion or cleanup coverage.

## Proposed bounded transaction contract

Before implementation, queue and API owners must review an explicit row-lock graph against issuance, check-in, booking confirmation, service start, catalog/staff changes, reminders and cleanup. Do not append branch locks inside the current user-first transaction, or nest independently committed scope transactions inside the deletion receipt.

1. Discover exact tenant/location scopes from every row the request can mutate: all owned tickets and bookings, not just cancellable tickets. Include linked plans, reservations and held allocations when assessing operational effects, and memberships/authority scopes affected by the deletion flag. Discovery is not authorization or proof of completeness. Bound row count, scope count, retries and transaction duration; an oversized or unavailable inventory must not be truncated into a successful resource claim. Review the failure/continuation policy before changing existing deletion admission.
2. Acquire branch locks in numeric ID order, then compatible tenant locks in numeric order, following the existing [catalog writer](../../backend/src/services/staffAccessResourceService.js). Preserve exact string IDs throughout; reject unsafe numeric identifiers. Re-read scope discovery after waits and tenant acquisition. New or changed scopes require rollback and a bounded fresh attempt, never acquiring an earlier-order lock after the user lock. Specify how branch creation and new ticket, booking or membership insertion are serialized; a repeated SELECT alone cannot close the phantom race.
3. Lock the user and revalidate current password/provider recency, account state and authenticated session requirements after waits. Explicitly determine how sessions revoked while waiting are handled; preflight authentication alone is not a current authorization proof. Acquire the remaining membership, ticket, booking, segment, protection, allocation and outbox locks in a documented stable order consistent with each competing writer. This proposal does not yet choose that complete order: implementation is blocked until the graph and both commit orders are tested.
4. Rediscover and verify ownership, scope, current ticket status and every linked resource binding under the held locks. Never skip locked work or treat missing/unknown provenance as empty inventory. Cancel only tickets still waiting or pending carry-over. Preserve active occupancy, actual timing and called-ticket attribution.
5. Commit receipt/account flag, sessions, inbox/device/channel suppression, ticket outcomes, segments, queue events, permitted unused-protection commands, affected branch revisions and outbox obsolescence on the **same client**. Advance each affected resource scope once for a real operational mutation; notification-only changes do not invent occupancy changes. Preserve the existing request ID and avoid duplicate ticket outcomes/events/commands on retries. A repeated request with no new operational change must not advance resource revisions; newly discovered cancellable work is not a no-op.
6. Refresh queues only after commit. A refresh failure remains retryable presentation/notification work and cannot rewrite the accepted transaction. No email, push provider or other external network call belongs under resource locks.

The [booking reminder](../../backend/src/services/bookingReminderService.js) locks user `FOR NO KEY UPDATE`, booking `FOR SHARE`, then its owned outbox row `FOR UPDATE`, and revalidates eligibility after waits. It takes no later branch/resource locks. Preserve compatible ordering and immediate inbox cleanup/future delivery suppression. A delivery already accepted by a provider cannot be recalled. Other dispatch paths still need independent compatibility checks.

## Unused protection and historical work

The existing [outcome service](../../backend/src/services/ticketResourceOutcomeService.js) checks live timing/allocation evidence and locks linked bookings/protection; converted bindings can require explicit service handling. Its optional booking cancellation must not become an implicit account-deletion policy. The [ledger](../../backend/src/repositories/resourceLedger.js) cancels protected reservations through scoped, operation-specific commands; its existing customer/expiry capabilities are not general system deletion authority.

A deletion adapter must prove exact customer ownership, ticket/booking/location linkage, resource scope and unstarted protected state before cancelling unused protection. Historical bindings still participate when tracking is disabled. Add a narrowly reviewed trusted deletion capability if required; do not spoof customer cancellation or expiry operation keys, accept client-provided authority, or open a second committed ledger transaction.

Converted reservations, held allocations, missing plans, inconsistent bindings and unknown lineage require explicit classification. Preserve current deletion receipt/admission semantics while specifying what can safely be cancelled and what remains unresolved. Do not silently drop these records, infer service starts/ends, release capacity, backfill plans or repair history. If safe integration needs a new denial, deferred cleanup or partial-progress policy, review that behavior separately before implementation; neither success-with-hidden-resource-failure nor an incidental new deletion rejection is an accepted contract here.

Booking cancellation, refunds and payment outcomes remain unchanged. Staff memberships/counter assignments are not deleted by this request slice. Assess the deletion flag's current authority effects and required invalidation; later membership removal or anonymization needs its own writer contract. Ledger revisions do not substitute for configuration, captured-plan or Queue Day/segment provenance watermarks; see the [watermark proposal](resource-provenance-watermarks.md).

## Implementation and acceptance boundaries

The first implementation slice may integrate the request and its waiting-ticket cancellation with a same-client resource adapter only after the lock graph, bounded inventory behavior and unresolved-protection policy are reviewed. Worker/anonymization/FK cleanup and historical reconciliation remain separate slices. Do not combine this work with invitation identity/authorization fixes, vendor UI or inference rollout.

Required PostgreSQL evidence includes:

- Deletion versus issue/check-in, call-next, booking confirmation/mutation, service start, reminder dispatch and staff/catalog mutation in both commit orders, including multiple tenants and branches. Demonstrate no lock inversion, skipped work or partial commit.
- Password changes, authentication/session revocation and provider authentication aging while waiting; fresh scope discovery after branch/tenant/user waits; branch and ticket/booking/membership insertion during discovery. Test the agreed retry/bound-exceeded behavior without weakening authentication or accepting truncated inventory.
- Exact adjacent BIGINT identities, duplicate requests, new eligible work on retry, and revision/event/command no-op behavior. Test historical protection with tracking disabled, protected versus converted bindings, unknown/missing linkage and retained overdue allocations/actual timing.
- Faults at receipt, revocation, suppression, cancellation, segment/event, reservation command, revision, outbox and commit boundaries: every same-client write rolls back. Postcommit refresh failure preserves the committed receipt.
- Existing HTTP gate, rate limit, authenticated identity, trusted reauthentication, response/cookie behavior, immediate inbox deletion and future notification suppression. Existing integration coverage must remain; new tests must exercise the resource adapter rather than mirror its helpers.

Source audit and document-link checks are the validation for this proposal. No new runtime tests, live deletion, production database inspection or cleanup were performed. Tracking and writer-coverage constraints remain false. Complete writer inventory, provenance watermarks, historical reconciliation, authoritative snapshot assembly, live consumers and AI/pool-concurrency pilots retain their independent gates.
