# Account-deletion resource writer proposal

Status: documentation-only proposal. Source baseline: main `d9ee0b01fd43fc3c9baba4f01310fdeff96ee43f` (merged PR #428). The follow-up incorporates late review findings; source inspection is not runtime race proof. No implementation, migration, cleanup run, resource activation or writer-coverage certification is supplied by this document. It narrows the account-deletion gap in the [coverage checkpoint](resource-writer-coverage-status.md); that checkpoint remains historical.

## Current request and separate cleanup

The authenticated [account route](../../backend/src/routes/accountRoutes.js) accepts only the caller's identity, retains its feature gate and rate limit, passes the trusted session, clears the browser session after success and returns HTTP 202. The [request service](../../backend/src/services/accountDeletionService.js) locks the user first, verifies the current password or recent supported provider authentication, then commits the deletion receipt, account flag, session revocation and notification suppression together.

The request immediately removes the customer inbox and browser push subscriptions, disables mobile registrations, disables notification channels on **all** owned tickets and bookings, obsoletes pending/retry/processing notification outbox entries and removes vendor reviews. It cancels only `waiting` and `pending_carry_over` tickets, closes their open segments and records cancellation events. It waits for locked tickets and rechecks status; it does not use `SKIP LOCKED`. Called or in-service work is not cancelled. Booking notification suppression does not change booking lifecycle status. Queue refresh runs after commit; its failure must not undo the receipt.

These writes currently have no branch resource revision or unused-protection reconciliation. The user-first order creates a source-derived compatibility concern with branch-first resource writers; this audit has not reproduced a deadlock. Existing [integration tests](../../backend/tests/accountDeletion.integration.test.cjs) cover authentication, retries, waiting-ticket cancellation, concurrent call-next and rollback, but do not certify resource integration.

The later [worker](../../backend/src/services/accountDeletionWorker.js), [inventory](../../backend/src/services/accountDeletionInventoryService.js) and [reviewed anonymization](../../backend/src/services/accountDeletionAnonymizationService.js) remain separate writers. Approved cleanup locks the existing deletion request before locking the user; the request path currently locks the user before upserting that receipt. Overlapping retry and cleanup can therefore invert request/user locks. This is a source-derived race, not a reproduced deadlock. Actor references, foreign keys and cascades require their own operational-effect inventory. Accepting a request does not prove erasure, retention completion or cleanup coverage.

## Proposed bounded transaction contract

Before implementation, queue and API owners must review an explicit row-lock graph against issuance, check-in, booking confirmation, service start, catalog/staff changes, reminders, direct customer deliveries, vendor-review mutations, ownership claims, device registration, session issuance, final administrative authority and cleanup. Do not append branch locks inside the current user-first transaction, or nest independently committed scope transactions inside the deletion receipt.

1. Discover exact tenant/location scopes from every row the request can mutate: all owned tickets and bookings, not just cancellable tickets. Include linked plans, reservations and held allocations when assessing operational effects, and memberships/authority scopes affected by the deletion flag. Discovery is not authorization or proof of completeness. Bound row count, scope count, retries and transaction duration; an oversized or unavailable inventory must not be truncated into a successful resource claim. Review the failure/continuation policy before changing existing deletion admission.
2. Acquire branch locks in numeric ID order, then compatible tenant locks in numeric order, following the existing [catalog writer](../../backend/src/services/staffAccessResourceService.js). Preserve exact string IDs throughout; reject unsafe numeric identifiers. Re-read scope discovery after waits and tenant acquisition. New or changed scopes require rollback and a bounded fresh attempt, never acquiring an earlier-order lock after the user lock. Specify how branch creation and new ticket, booking or membership insertion are serialized; a repeated SELECT alone cannot close the phantom race.
3. For an existing receipt, lock the deletion request before the user, sharing that order with approved cleanup. Define first-request/absent-receipt serialization explicitly: an upsert after a user lock must not recreate the inverse order. Include cleanup's branch-owned writes in the complete graph; preserving its request/user order alone does not certify compatibility with branch-first writers. Then lock the user and revalidate current password/provider recency, account state and authenticated session requirements after waits. Explicitly determine how sessions revoked while waiting are handled; preflight authentication alone is not a current authorization proof. Acquire the remaining membership, ticket, booking, segment, protection, allocation and outbox locks in a documented stable order consistent with each competing writer. This proposal does not yet choose that complete order: implementation is blocked until the graph and both commit orders are tested.
4. Rediscover and verify ownership, scope, current ticket status and every linked resource binding under the held locks. Never skip locked work or treat missing/unknown provenance as empty inventory. Cancel only tickets still waiting or pending carry-over. Preserve active occupancy, actual timing and called-ticket attribution.
5. Commit receipt/account flag, sessions, inbox/device/channel suppression, ticket outcomes, segments, queue events, permitted unused-protection commands, affected branch revisions, outbox obsolescence and deletion of the customer's vendor reviews on the **same client**. Advance each affected resource scope once for a real operational mutation; notification-only changes do not invent occupancy changes. Preserve the existing request ID and avoid duplicate ticket outcomes/events/commands on retries. A repeated request with no new operational change must not advance resource revisions; newly discovered cancellable work is not a no-op.
6. Refresh queues only after commit. A refresh failure remains retryable presentation/notification work and cannot rewrite the accepted transaction. No email, push provider or other external network call belongs under resource locks.

The [booking reminder](../../backend/src/services/bookingReminderService.js) locks user `FOR NO KEY UPDATE`, booking `FOR SHARE`, then its owned outbox row `FOR UPDATE`, and revalidates eligibility after waits. It takes no later branch/resource locks. Preserve compatible ordering and immediate inbox cleanup/future delivery suppression. A delivery already accepted by a provider cannot be recalled. The [generic dispatcher](../../backend/src/services/queueNotificationOutboxDispatcher.js) has a concrete gap: `runBatch` commits its claim before dispatch, and its non-booking email/web-push/FCM paths do not revalidate current outbox status/lease and the deletion flag together before sending. Deletion can obsolete a processing intent before that stale claim reaches the provider. This is not a delivery already accepted by the provider, and current suppression writes do not prove it is prevented.

Before the first deletion resource implementation, define and verify a generic-dispatch serialization protocol against deletion: current recipient/account state, owned lease/outbox eligibility, ticket/channel eligibility, registration state and inbox writes must participate. A standalone pre-send SELECT leaves a check/send race. Ensure an earlier claim cannot repopulate the deleted inbox or start a new provider send after deletion commits. Bound provider work without holding branch/resource locks; coordinate any dispatcher implementation separately with the API owner. Both commit orders and pauses after claim and after eligibility validation must be covered for email, web push and FCM. The first implementation gate also covers direct postcommit customer delivery paths, not only this dispatcher. In the [booking service](../../backend/src/services/bookingService.js), `cancelCustomerBooking` releases its scoped transaction before `notifyCustomerBookingCancellation` sends email/SMS and schedules customer push from the captured booking. Deletion can commit in that gap; neither the released branch lock nor a captured notification flag proves current eligibility. Enumerate direct and outbox customer delivery entry points, callbacks and aliases, and require the same deletion serialization guarantees before integration. Include pauses after business commit and between successive channel sends, plus push/inbox callbacks. Current account, recipient/channel/device and inbox eligibility must be established through the reviewed protocol; one earlier check cannot authorize later sends. Do not claim complete suppression while a known direct path remains ungated. Provider-accepted delivery remains separately classified.

The [rating service](../../backend/src/services/ratingService.js) currently checks booking/ticket ownership and service eligibility before calling [review insertion](../../backend/src/repositories/ratings.js) outside a shared deletion transaction; insertion does not explicitly lock and revalidate the current user's deletion state. The foreign key can acquire an implicit user key-share lock, which does not check `deletion_requested_at` or prevent insertion after the deletion request commits. An already-authenticated request can therefore insert after deletion removes existing reviews. Before the first resource slice, define a compatible user/deletion serialization protocol for both booking and queue-ticket review creation, including all aliases. Revalidate current account/deletion state, ownership and eligibility after waits, and commit creation through the same held protocol so it cannot publish after deletion wins. If creation commits first, deletion must remove that review on its own transaction client; if deletion commits first, creation must be denied without insertion. Include these locks in the complete graph rather than adding user locks after incompatible review/operational locks. Review deletion is an existing account side effect, not an occupancy change or an excuse to advance resource revisions. Runtime rating changes remain separately coordinated.

## Additional concurrent writers required before integration

**Ownership claims.** The [account claim route](../../backend/src/routes/accountRoutes.js) calls [claimTicketForUser](../../backend/src/repositories/tickets.js) using the authenticated user; the repository updates `user_id` without a current deletion-state check. [Private mobile-link acceptance](../../backend/src/services/mobileTicketLinkService.js) locks ticket then link and verifies ownership, status, project/environment and token usability, but does not revalidate the receiving user's deletion state. These are ownership updates to existing tickets, not new-ticket insertion. Include both paths and aliases in scope discovery and the complete lock graph. Define compatible current-user/deletion serialization before assigning ownership, and rediscover scopes after waits. A claim committed first must be included in deletion's cancellation/notification suppression according to current ticket status; deletion committed first must prevent attachment. Preserve ticket/link order, one-time consumption, environment boundaries and called occupancy; never introduce an inverse user/ticket lock order or cancel called work to hide the race.

Developer API attachment is a separate ownership writer, not an alias of ordinary ticket claims. The [mobile invitation and Sandbox QR routes](../../backend/mobile/ticketRoutes.js) call [acceptMobileInvitation and claimMobileTicketByVerificationCode](../../backend/src/repositories/developerQueues.js), updating `developer_api_tickets.linked_user_id` without current deletion validation. Invitation email matching, waiting/called eligibility, linking/data-deletion flags, project scope and Sandbox-only QR/environment restrictions must survive the reviewed protocol. Discover these separate-table account references, linked notifications and cleanup/FK effects explicitly; ordinary `tickets` discovery cannot account for them. Require compatible current-user/Developer API-ticket serialization and both commit orders, including idempotent invitation acceptance. Deletion-first must deny new attachment; attachment-first must follow a separately reviewed retention/unlink/suppression policy on the same applicable transaction boundary. Do not silently map Developer API statuses/resources onto vendor tickets or auto-cancel called work. Project/environment separation may exclude a Developer API ticket from vendor resource revisions only with verified scope independence; it does not exclude account deletion's identity/privacy obligations.

The deletion inventory already dynamically discovers numeric user-like columns and user foreign keys, including populated Developer API links and Developer Account ownership. These sources are not approved safe-cleanup/best-effort anonymization sources at this baseline; discovery cannot authorize their disposal. The [Developer API retention worker](../../backend/src/services/developerApiRetentionService.js) clears identity/link fields only for terminal tickets older than 90 days, not immediate deletion or active-ticket/owner retirement. Explicitly review account/project/key/webhook continuity, frozen/closed/transfer outcomes and retained obligations; no one of these policies is selected here.

**Device registration.** [Browser subscription upsert](../../backend/src/repositories/pushSubscriptions.js) and [mobile registration upsert](../../backend/mobile/pushRegistrationRepository.js), reached through account POST and [mobile PUT](../../backend/mobile/pushRoutes.js), can create/reactivate devices from an earlier authenticated request without checking current deletion state. The Sandbox mobile path already locks the user for its device quota, but does not revalidate deletion after that wait; preserve quota/environment rules and include it in the protocol. Serialize registration, reactivation and ownership reassignment with deletion, including shared endpoint/token/installation conflicts. Registration-first must be deleted/disabled by deletion; deletion-first must deny registration without an active record. Dispatch-side device checks alone do not serialize these writers. Enumerate customer and tenant/operator delivery selectors so vendor membership cannot authorize pushes to a deleting user through a recreated subscription.

**Session issuance.** [createAuthSession](../../backend/src/services/sessionService.js) rejects a deletion flag on the supplied user object, then [inserts an active session](../../backend/src/repositories/authSessions.js) without rereading current user state. [Password/OAuth authentication](../../backend/src/routes/authRoutes.js) and [MFA completion](../../backend/src/services/mfaFlowService.js) can supply a previously loaded object; registration, refresh/rotation and other surface-specific session entry points also require inventory. Define shared account/session ordering and current deletion-state validation after waits on the same client as issuance/rotation. Issuance-first sessions must be revoked by deletion; deletion-first must deny issuance with no active server session, refresh credential or access token returned. Middleware rejecting later use is not evidence that no active session was created. Preserve current authentication, MFA, expiry, surface and trusted reauthentication requirements; do not allow captured user state or FK key-share locks to substitute for deletion validation.

**Final administrative authority.** Setting the deletion flag immediately excludes the account from normal authenticated access while stored memberships remain. The [staff writer](../../backend/src/services/staffAccessResourceService.js) protects the final tenant owner; [Platform user management](../../backend/src/routes/platformRoutes.js) protects the last active Platform Admin. Deletion must not implicitly bypass those invariants. Before integration, owners must review an explicit deletion admission, transfer or continuation policy for sole owners and last active Platform Admins, including the current eligibility definition, excluded/suspended/deleting/Sandbox accounts and the requesting account's multiple tenants. Define compatible locks held through validation and commit against concurrent deletion, transfer, role/status/member edits and Platform suspension. A count read alone permits two administrators to pass concurrently. This proposal implements no new rejection or transfer policy: changing the existing receipt admission requires a separately reviewed product/API decision, and implementation remains blocked until final-authority behavior and ordering are settled. Do not silently orphan a vendor, remove all platform governance or automatically transfer ownership.

Developer Account ownership is also part of final-authority admission. The [Developer Account schema](../../database/migrations/20260915_add_developer_accounts.sql) has a unique sole `owner_user_id` referencing users with `ON DELETE CASCADE`, plus a single-active-owner membership invariant; [projects](../../database/migrations/20260915_add_developer_projects_and_keys.sql) cascade from the account. Platform role edits preserve Developer roles while permitting app roles, so a Developer owner with app access cannot be excluded from this audit by portal label alone. Define reviewed admission/transfer/continuation and later cleanup/cascade policy for these owners before integration, with compatible locks on account/owner/membership/project reference changes and current authentication surfaces. Include ownership creation/transfer, membership/status changes and cleanup in the complete graph; preserve uniqueness and environment/account boundaries. Flagging deletion can revoke access immediately, and eventual user removal can cascade or be blocked by references. Neither is an approved account/project disposal policy here. No automatic project deletion, ownership transfer, role removal or new denial is implemented by this proposal.

Developer credential and submission writers are separate from ticket attachment and auth-session issuance. The [Developer project routes](../../backend/src/routes/developerProjectRoutes.js) create API keys through [createApiKey](../../backend/src/repositories/developerProjects.js), register webhooks through [createRegistration](../../backend/src/repositories/developerWebhooks.js), and submit production applications; these paths can persist actor references using a user captured before deletion. Key/webhook creator and [production submission/reviewer references](../../database/migrations/20260924_add_developer_production_approval.sql) can restrict later user removal. Include key issuance/revocation, webhook registration/secret rotation/disabling/replay, production draft/submission, project/profile/queue/test-account mutations and all applicable Developer HTTP/internal aliases in an explicit writer inventory, not as presumed aliases of session creation. Revalidate current actor/account/membership/project grants under compatible held ordering through persistence, audit/idempotency writes and credential-return or provider-dispatch boundaries. Deletion-first must prevent a stale actor from creating a credential, returning a usable newly issued secret, submitting work or adding an unreviewed cleanup-blocking reference. Mutation-first requires separately reviewed credential/webhook continuity, revocation and reference-retention outcomes during deletion. Do not infer that user-session revocation revokes project API keys or webhook secrets; do not automatically revoke another owner's project credentials. Preserve environment, approval, scope/profile restrictions, key quotas, secret confidentiality, replay controls and current project/account status rules. The separate [Developer authentication middleware](../../backend/src/middleware/developerAuth.js) reads session/user/membership without a visible explicit deletion flag check or held locks at this baseline; ordinary app middleware must not be assumed to protect it. Key/webhook creation persists outside a shared actor-validation transaction and logs/returns secrets later, so log or response failure does not roll back the inserted credential. Webhook URL validation introduces a network wait before persistence. Production submission holds application/draft protections and rechecks the snapshot, but that does not hold current actor/owner authorization; preserve its pending/snapshot conflict rules. Include pauses after these waits, after persistence before logging, and before secret response in the evidence. Full inventory and the reviewed shared protocol remain implementation gates, not a statement that every existing writer has this defect.

**Review revisions and disputes.** In addition to creation, [review revision](../../backend/src/repositories/ratings.js) locks the review before inserting a revision whose actor FK references the user, potentially reversing deletion's user-before-review order. [Dispute creation](../../backend/src/services/ratingService.js) reads the review before the repository's separate transaction inserts a polymorphic dispute and updates moderation; the dispute's rating ID does not enforce review existence through a review FK. Include revision/dispute paths and aliases in the account/review lock graph, revalidate current account, participant ownership, review existence and existing time/one-revision rules after waits, and commit through compatible held serialization. If the mutation commits first, deletion must apply its reviewed review/revision/dispute deletion-or-retention policy atomically; deletion-first must deny the mutation without a revision or orphan dispute. Specify retained dispute/actor-reference handling against reviewed cleanup inventory rather than silently cascading or deleting beyond current policy. Existing revision/dispute behavior and retention require explicit decisions before implementation; no new retention policy is introduced here.

Privileged review writers also participate. [Vendor review visibility and reply routes](../../backend/src/routes/vendorRoutes.js) reach the review repository; reply records `vendor_replied_by_user_id`, while visibility mutates the target review even without an actor FK. [Platform dispute resolution](../../backend/src/routes/platformRoutes.js) and [repository resolution](../../backend/src/repositories/ratings.js) record `resolved_by_user_id` and update review moderation. Inventory both actor-account deletion and reviewed-customer deletion, current privileged grants, target review/dispute existence, retained actor references and moderation effects. Require compatible actor/user/grant/review/dispute ordering and current-state revalidation after waits for vendor reply/visibility and Platform resolution/moderation, including all HTTP/internal aliases. If deletion wins, stale authorization cannot permit a deleting actor to write, or mutate/recreate a removed target; if the privileged mutation wins, deletion must follow the explicit review/actor/dispute retention contract. Preserve existing vendor scope, permissions, moderation rules and reply limits. A captured staff/admin role or customer-only protocol does not certify these writers.

The Platform mutation gate extends beyond rating moderation and final-owner role edits. The [production-approval route](../../backend/src/routes/platformRoutes.js) checks permission before a transaction that reviews the submission and writes an audit record with captured actor identity; [reviewProductionApproval](../../backend/src/repositories/developerProjects.js) persists `reviewer_user_id`. This does not establish a held current actor/deletion/grant check. Enumerate all applicable Platform Admin mutation families, including Developer production approval and webhook controls, vendor approvals/suspensions, user/session/security/membership management, plan/subscription/entitlement/credit policy, catalog/settings, moderation/disputes, queue repair, maintenance/AI policy and deletion-review/cleanup/report actions, plus service/internal aliases and asynchronous continuations. For each, classify actor and target deletion effects, held actor/current grants, lock order, reference/retention and audit/idempotency effects, provider boundaries and both commit orders. Permission middleware, a final-authority count or one moderated-review protocol cannot certify unrelated privileged mutations. Deletion-first must prevent a stale deleting actor from approving or mutating governed work; mutation-first must follow explicit audited reference and target-retention policy. Preserve current step-up/MFA, reasons, permissions, scoped target checks, release controls, idempotency and system-capability distinctions. No policy-setting change, audit erasure, approval rollback or activation is authorized by this proposal. Unenumerated/unsupported mutation paths block a completeness claim and require owner review before the first integration slice.

These five writer families are first-slice prerequisites alongside the earlier lock, delivery and protection gates. Inventory their HTTP/mobile aliases, callbacks, internal/system consumers and authorization changes; unsupported or unenumerated paths remain gaps, not exclusions inferred from names. Coordinate runtime changes with API, mobile and Platform owners. Account side effects do not by themselves justify resource revision increments; classify real authority/operational changes explicitly.

## Unused protection and historical work

The existing [outcome service](../../backend/src/services/ticketResourceOutcomeService.js) checks live timing/allocation evidence and locks linked bookings/protection; converted bindings can require explicit service handling. Its optional booking cancellation must not become an implicit account-deletion policy. The [ledger](../../backend/src/repositories/resourceLedger.js) cancels protected reservations through scoped, operation-specific commands; its existing customer/expiry capabilities are not general system deletion authority.

A deletion adapter must prove exact customer ownership, ticket/booking/location linkage, resource scope and unstarted protected state before cancelling unused protection. Historical bindings still participate when tracking is disabled. Add a narrowly reviewed trusted deletion capability if required; do not spoof customer cancellation or expiry operation keys, accept client-provided authority, or open a second committed ledger transaction.

Converted reservations, held allocations, missing plans, inconsistent bindings and unknown lineage require explicit classification. Preserve current deletion receipt/admission semantics while specifying what can safely be cancelled and what remains unresolved. Do not silently drop these records, infer service starts/ends, release capacity, backfill plans or repair history. If safe integration needs a new denial, deferred cleanup or partial-progress policy, review that behavior separately before implementation; neither success-with-hidden-resource-failure nor an incidental new deletion rejection is an accepted contract here.

Booking cancellation, refunds and payment outcomes remain unchanged. Staff memberships/counter assignments are not deleted by this request slice. Assess the deletion flag's current authority effects and required invalidation; later membership removal or anonymization needs its own writer contract. Ledger revisions do not substitute for configuration, captured-plan or Queue Day/segment provenance watermarks; see the [watermark proposal](resource-provenance-watermarks.md).

## Implementation and acceptance boundaries

The first implementation slice may integrate the request and its waiting-ticket cancellation with a same-client resource adapter only after the complete request/cleanup lock graph, bounded inventory behavior, unresolved-protection policy and deletion serialization for generic dispatch, direct customer deliveries, customer and privileged review mutations, ordinary and Developer API ownership claims, device registration and session issuance are reviewed and verified. Developer credential/submission and all applicable Platform Admin mutation protocols must also be established. Tenant/Platform/Developer Account final-authority admission/transfer/continuation and cleanup/cascade policy must be settled with compatible locking. The entry-point inventory must cover known callbacks/aliases before any complete notification or review-suppression claim. Worker/anonymization/FK cleanup and historical reconciliation remain separate slices. Do not combine this work with invitation identity/authorization fixes, vendor UI or inference rollout.

Required PostgreSQL evidence includes:

- Deletion versus issue/check-in, call-next, booking confirmation/mutation, service start, reminder dispatch and staff/catalog mutation in both commit orders, including multiple tenants and branches. Demonstrate no lock inversion, skipped work or partial commit.
- Deletion retry versus approved cleanup in both commit orders, including absent first receipt, duplicate request and concurrent cleanup discovery. Preserve receipt identity and current authentication; demonstrate no inversion-induced abort or `needs_attention` outcome. Cleanup remains a separate implementation slice, but its shared ordering is a prerequisite.
- Generic notification claims paused before send and after eligibility validation versus deletion in both orders, across email/web push/FCM and inbox/device writes. Demonstrate that a stale claim cannot send or recreate inbox state after deletion commits; distinguish already accepted provider delivery.
- Direct postcommit booking cancellation delivery paused after the business commit, before each email/SMS/push send and within push/inbox callbacks versus deletion in both orders. Extend this evidence to every enumerated direct customer delivery entry point; no callback may publish inbox data or begin a new provider send after deletion wins.
- Booking and queue-ticket vendor-review creation paused after ownership/service eligibility reads and before insertion versus deletion in both orders. Creation-first is removed in deletion's atomic commit; deletion-first is denied without a new public review. Include existing authenticated requests, aliases, rollback of review deletion and later cleanup inventory consistency.
- Browser claim and private mobile-link acceptance paused before ownership update versus deletion in both orders, including new scope attachment after discovery, waiting/called status, one-time token consumption and environment isolation. Deletion-first cannot attach; claim-first is rediscovered without releasing called occupancy.
- Developer API invitation and Sandbox QR attachment paused before `linked_user_id` update versus deletion in both orders, including idempotent acceptance, invitation email/current identity, project/environment restrictions, ordinary-ticket discovery exclusion and later cleanup references. No new attachment after deletion wins; attachment-first follows the reviewed unlink/retention/suppression policy without vendor-ticket cancellation assumptions.
- Browser/mobile registration and reactivation versus deletion in both orders, including shared token/endpoint reassignment, Sandbox quota waits and tenant/operator notifications. No active device record or inbox recreation may survive a deletion-first registration attempt.
- Password/OAuth/MFA session issuance, registration login and refresh/rotation versus deletion in both orders, paused after user capture and before persistence/token return. Verify all issuance-first sessions revoke and deletion-first creates no active session or usable returned credential.
- Sole-owner and last-active-Platform-Admin cases under the reviewed admission/continuation policy, plus concurrent deletions, transfer, promotion/demotion, membership/activity edits and suspension across multiple tenants. Prove stable final authority rather than an unlocked count or invented transfer.
- Developer Account owner deletion under the reviewed admission/continuation/cascade policy versus account creation, ownership transfer, membership/status/project changes and cleanup in both orders. Verify unique/single-active owner invariants and mixed Developer/app-role access; preserve projects unless explicit reviewed disposal authorizes otherwise.
- Developer API key creation and webhook registration/secret rotation/replay plus production draft/submission paused after authentication/grant reads and before persistence, audit/idempotency commit, secret return or provider dispatch versus deletion in both orders. Verify no usable new credential/submission/reference after deletion wins and explicit mutation-first credential/reference policy; extend evidence to every enumerated Developer mutation/alias.
- Platform production approval and every other applicable enumerated privileged mutation family paused after middleware/step-up authorization and before target/actor-reference/audit/idempotency writes versus actor and target deletion in both orders. Verify held current actor/grants, no deletion-first approval or stale privileged mutation, compatible lock ordering and reviewed mutation-first retention outcomes; cover continuations/provider boundaries without silently reversing approvals.
- Review revision and dispute mutation paused after eligibility reads and review locks versus deletion in both orders. Prove no user/review inversion, no revision or orphan dispute after deletion wins, and documented retention/actor-reference handling when mutation wins. Preserve time/ownership/one-revision rules and reviewed cleanup consistency.
- Vendor reply/visibility and Platform dispute resolution/moderation versus actor deletion and target-customer/review deletion in both orders, paused after privileged authorization and before write. Verify current grants/actor state, target existence, no stale privileged writes or orphan resolution, and reviewed actor/reference/retention handling when mutation wins.
- Password changes, authentication/session revocation and provider authentication aging while waiting; fresh scope discovery after branch/tenant/user waits; branch and ticket/booking/membership insertion during discovery. Test the agreed retry/bound-exceeded behavior without weakening authentication or accepting truncated inventory.
- Exact adjacent BIGINT identities, duplicate requests, new eligible work on retry, and revision/event/command no-op behavior. Test historical protection with tracking disabled, protected versus converted bindings, unknown/missing linkage and retained overdue allocations/actual timing.
- Faults at receipt, revocation, suppression, cancellation, segment/event, reservation command, revision, outbox, vendor-review deletion and commit boundaries: every same-client write rolls back. Postcommit refresh failure preserves the committed receipt.
- Existing HTTP gate, rate limit, authenticated identity, trusted reauthentication, response/cookie behavior, immediate inbox deletion and future notification suppression. Existing integration coverage must remain; new tests must exercise the resource adapter rather than mirror its helpers.

Source audit and document-link checks are the validation for this proposal. No new runtime tests, live deletion, production database inspection or cleanup were performed. Tracking and writer-coverage constraints remain false. Complete writer inventory, provenance watermarks, historical reconciliation, authoritative snapshot assembly, live consumers and AI/pool-concurrency pilots retain their independent gates.
