# Vendor current-period usage

Reports and Subscription must display authoritative current subscription allowance-period usage across all tenant locations. The previous servedToday/monthly-limit calculation combines a daily service statistic with a monthly allowance; live tenant5 reconciliation found 1 served ticket for October14 versus18 ticket admissions in the monthly window.

GET `/api/billing/tenant/:tenantSlug/usage` requires authentication, active membership in the requested tenant, and `tenant.reports.read`. Existing owner/admin/staff report readers are permitted. The response matches `shared/tenantPeriodUsage.ts`: explicit tenant identity and subscription/plan identity, database observation time, nullable half-open monthly window, availability, and the queueTickets/serviceBookings resources with limit, canonical used, observed created admissions, and accounting status. Used is the existing capacity service's base-allowance projection after ledger reconciliation and eligible credits; the client must not add diagnostics, count served tickets, clamp usage, or infer a calendar-month window. ObservedUsed remains distinct from used when credits/reversals apply.

The projection reuses the existing REPEATABLE READ READ ONLY capacity calculation. An invalid, missing, expired or ambiguous current period is unavailable with null usage and null period. A valid empty period is zero. Legacy subscription limits, annual billing monthly anchors, cancellations, booking conversions, group-funded exclusions, and credit/reversal accounting retain canonical semantics. No new writer, reset, backfill, credit activation, or provider action is introduced.

This narrow operational read is independent of the gated credit/capacity experience. It excludes prices, purchases, lots, credit provenance, override reasons, enforcement controls, warnings and commercial history. Existing capacity and checkout routes remain gated. Vendor PR #444 consumes this read in both Reports and Subscription, with tenant/actor query scope, current-window validation, error/unavailable states and no daily fallback. Keep daily queue service statistics separate.
