# Staff access-edit resource writer

This slice covers the existing vendor staff PATCH endpoint's role, active status and location grants. Invitation and its commercial quota/absence locking remain separate B2 gaps. It adds no public payload fields, migrations, resource activation or workflow operation.

`staffAccessResourceService` uses the catalog transaction: all current branches in numeric ID order with `FOR NO KEY UPDATE`, then tenant `FOR UPDATE`, then current actor grants. Branch discovery is repeated after tenant acquisition; concurrent insertion rolls back with a reload/retry conflict. The requesting actor must still have `tenant.staff.manage`; role edits require current owner status. Actor user/membership SHARE locks remain held until commit. The target user is SHARE locked and selected membership UPDATE locked, then read after waits. Compatible user locks permit reciprocal cross-vendor edits without global-user lock inversion. No global profile or account role write is added.

Existing self-edit, protected-owner, single-owner, role/location and active-branch rules remain. Inactive/suspended target cleanup remains possible. An explicit false status deactivates; omitted status retains current state. Deactivation retains stored location/counter grants, and simultaneous location replacement remains the existing no-op for the inactive membership. Role normalization retains the existing owner/admin/staff behavior. Requested grants are scoped to active current vendor branches, even on an otherwise identical save. Exact string identifiers avoid adjacent BIGINT aliasing; unsafe numeric request IDs reject before conversion.

Role/status changes affecting vendor-wide administrator/owner access advance all current branches. Staff role/status changes advance the union of explicit grants and counter-assignment branches. Location-only changes advance added/removed branches once, without altering counter assignments. A logical no-op neither rewrites assignments (including their source metadata), advances a revision nor enqueues an access notification. A real access change without any affected branch can still enqueue its existing notice without inventing a branch revision.

Membership changes, location replacement, affected branch revisions and existing staff-access email outbox intents use the same client and commit together. Membership, assignment, revision, outbox or commit failure rolls back all effects. Email delivery remains asynchronous. The HTTP response remains `{userId}` with status 200. Preflight route permissions do not replace the locked current authorization.

Calling, ticket attribution and existing allocations are unchanged. Deactivation or grant removal does not cancel called work or release occupancy; expected end remains only a forecast. Counter administration and staff removal share branch-first ordering. Existing tenant-first invitation can retain its key-share-compatible branch FK behavior, but is not certified by this slice.

## Verification and remaining gates

Disposable PostgreSQL scenarios cover deduplicated revisions, status and admin transitions, exact/no-op grants, inactive grant semantics, protected owners, current actor roles, foreign locations, rollback at each write/commit boundary, actor revocation after branch/tenant waits, suspension after user waits, target promotion while waiting, held actor/target grants, real counter-assignment races in both commit orders, concurrent branch insertion/retry, reciprocal vendor changes, adjacent BIGINTs and held overdue allocation/attribution preservation. HTTP regression checks exact request delegation, response and domain denial.

These are local adapter/route checks, not authenticated live acceptance or complete writer certification. Account deletion, invitation, Platform/maintenance writers, complete configuration/plan/lineage watermarks, historical reconciliation, B1 live consumer and B3 authoritative assembly retain independent prerequisites. Production tracking and coverage constraints remain false; no pool concurrency pilot, ready snapshot, repair, forecast/capture or customer inference is introduced.
