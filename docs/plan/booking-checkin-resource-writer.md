# Booking check-in resource writer

Customer arrival and vendor check-in now enter the location-first booking transaction. Customer ownership/deletion/suspension and vendor active membership, queue permission and staff branch/active-counter assignment are rechecked under the location lock. The booking is reloaded under a row lock and checked against the selected persisted scope. Current business and branch availability are reloaded on the transaction client, including branch self-check-in configuration for customers.

Existing check-in rules remain: confirmed/rescheduled state, fifteen-minute early/late window, vendor late override, verified manual payment for customer arrival and queue intake policy. Customer retries return the existing ticket after actor/ownership checks; staff duplicates reject. New check-ins require valid protected resource binding when applicable. Ordinary disabled-resource bookings keep their existing composition behavior.

Ticket creation and its allowance, immutable booking service-plan capture, booking arrival fields and scope revision commit together. A plan/admission/protection failure rolls back everything. Competing arrival/no-show transactions serialize. Notifications, auto-pause and snapshot publication remain postcommit. No durable notification or whole-request HTTP idempotency layer is introduced.

Arrival retains the immutable protected reservation, even after tracking disable, and does not create/convert an allocation or release occupancy. Service-plan capture retains its existing metadata contract. Actual service start must separately validate plan/configuration and reservation compatibility before allocation; draft configuration changes are not reconciled by arrival. Calling also remains distinct from allocation. Expected end never releases occupancy.

The action no longer runs unrelated lazy expiry before authorization. Tracking and writer coverage remain disabled until explicit session allocation/release, other payment writers, configuration/reconciliation and ready snapshot inventory are complete. No activation/backfill, inference hook or customer estimate change.

Disposable PostgreSQL tests use the real ledger migration/adapter and booking service-plan capture with minimal booking/queue transaction fixtures. They cover protection retention/no allocation, plan/item identity, concurrent staff/customer arrival, customer retry, no-show/late-check-in contention, plan failure rollback, staff assignment, locked ownership/suspension, current business/branch/self-check-in/payment/queue gates, missing/converted protection and ordinary behavior. Production queue creation/allowance internals retain their own tests; this fixture tests their transaction participation. Live authenticated resource check-in is not claimed.
