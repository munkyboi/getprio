# Location-bound legacy paid queue issuance

New paid checkouts store the server-resolved branch ID and canonical slug in the payment payload, with a server-written locationBindingVersion 1 metadata marker. A client payload ID cannot override that capture. OTP-keyed reuse preserves the existing payload/Queue Day/trust marker; metadata merge cannot promote an old payload. Missing IDs or unsupported legacy binding versions reject for reconciliation. Existing enforced Queue Day bindings still determine their scope and must agree with any versioned branch binding. Historical unversioned payload IDs do not become authority; older unbound checkout rows remain a separate writer/reconciliation gap.

Versioned legacy/shadow checkout fulfillment now locks the stored location before the payment and compares the current payment tenant, provider checkout, Queue Day, branch ID and binding version after the wait. Tenant policy and authenticated customer state retain shared row locks through issuance. Current branch mode/activity, tenant/subscription/customer eligibility, branch-local date, manual closure/pause, operating hours and intake threshold determine admission. A checkout created in legacy mode cannot silently admit into a subsequently enforced Queue Day. The hours lock is acquired before capturing one instant for date and hours admission. Existing hours rows are read with shared locks; this does not certify all catalog/settings writers or activation readiness.

Scoped sequence/ticket creation, existing allowance consumption and email admission, ticket-created event/webhook, payment linkage and scope revision commit together. Current branch slugs are returned for fulfillment and later paid sync. Duplicate callbacks reuse issued/refund-pending outcomes; a durable billing receipt retries an unissued versioned checkout after rollback. Unavailable admission records the existing paid/refund-pending marker and releases the hold atomically. This does not execute a monetary refund. Missing/deleted scope or changed binding rejects for reconciliation instead of guessing a primary branch. Unexpected event/webhook/allowance/payment failures roll back. Ticket issuance never allocates resources, and blocked admission never releases existing occupancy or converted bindings.

## Validation and boundaries

Dedicated PostgreSQL tests use actual payment/ticket/persistence/ledger and hours SQL, with minimal transactional allowance/lifecycle/event fixtures and synthetic provider-paid input. Regressions cover concurrent duplicate fulfillment, branch rename/current slug, local date, active scope/mode/intake/hours/threshold/subscription/customer admission, rollback and replay of the same durable receipt, allowance-release failure, retained occupancy, location-before-payment locking, changed branch/version bindings and exclusion of unversioned historical payload IDs. The checkout unit test verifies server binding overrides a supplied client ID.

Backend coverage suite: 954 passed, seven unrelated opt-in skips, 961 total. Focused ESLint, backend typecheck and diff checks passed. Aggregate coverage is 64.45 percent lines/statements, 68.53 percent branches and 60.25 percent functions; no 80 percent threshold claim. This is not a production bootstrap, provider-policy, monetary refund or authenticated live payment proof. Legacy unversioned paid and zero-fee public/customer/developer writers remain gaps. Tracking and coverage stay disabled, producer v1 remains not_ready, and no activation/backfill/ready inventory or inference/capture/export contract change is introduced.
