# Counter configuration writer (B2.1)

Counter create/update/delete now enter one location-first resource transaction before touching counters, assignments or quota. Server-resolved branch/tenant and authenticated actor IDs bind the transaction. The branch takes `FOR NO KEY UPDATE`, permitting tenant-first staff changes to insert branch foreign-key grants; the tenant takes `FOR UPDATE` before user/membership grants. This fences new FK-backed subscriptions and serializes tenant policy/assignment administration, including an absent subscription. Counter administration remains available for inactive branches/vendors under its existing permissions.

The actor must retain `tenant.counter.manage` in a current active vendor membership; actor and selected assignee user/membership grants remain shared-locked through commit. Selected assignees must be active, nondeleted, nonsuspended members of this vendor. Staff assignees receive the existing explicit branch grant in the same transaction. Removing counter assignments retains those explicit grants, matching current behavior. Identifiers remain exact strings through counter and automatic branch-assignment repositories; unsafe numeric IDs are rejected before string conversion.

Creation keeps its existing active-counter quota check even for an inactive new counter. Any update which activates an inactive counter checks current quota, including omitted `isActive` (which continues to default true). Already-active editing, explicit deactivation and deletion do not introduce a new quota check. Quota uses the same client and existing billing selection: active status is preferred over past-due/unpaid/other subscriptions, newest update within a status group; only an active selected subscription supplies entitlements. Subscription JSON overrides plan JSON; absent/nonactive subscription gives zero counters. Counter quota does not add commercial override semantics.

All existing tenant subscription rows are locked in ID order with `FOR UPDATE NOWAIT` before the selected subscription is reread. Its plan is locked `FOR SHARE NOWAIT` before reading entitlements. These locks and the tenant FK fence stabilize selection through commit, including subscription replacement. Subscription/plan writer conflicts return sanitized retryable `409 COUNTER_POLICY_BUSY` and roll back. They do not wait in a subscription-first/tenant-first lock cycle.

Counter row changes, counter assignment replacement, automatic staff branch grants and one branch ledger revision advance commit together. An identical logical update with no missing explicit branch grant is a no-op: it does not rewrite assignments or advance the revision. Repairing an absent explicit branch grant for a currently selected staff member is a logical mutation and advances once. The shared transaction may initialize an absent ledger scope at its existing revision 1; that initialization is not a coverage assertion. Validation, assignment, quota, final revision or commit failure rolls back all writes.

HTTP statuses and write response shapes remain create 201, update 200 and delete 204; write responses retain an empty aggregated `assignedUserIds` field. Create and update retain their respective existing slug normalization. Counter deactivation preserves called-ticket attribution and permits existing inactive-counter resolution. Deletion preserves the existing ticket foreign-key `SET NULL` behavior and explicit legacy-null lane; it does not release allocations, cancel reservations or infer service completion. Dispatch and counter administration serialize on the branch lock and existing counter row locks.

## Verification and boundaries

Focused disposable PostgreSQL tests use the real resource foundation migrations and counter/assignment/FK semantics. They exercise quota creation/reactivation races, status priority, entitlement overlay, missing subscription/plan, subscription/plan contention, absent/new subscription after lock waits, actor revocation after branch/tenant/user waits, held actor/assignee grants, tenant-first staff-removal compatibility, write/revision rollback, no-op updates, called attribution/overdue allocation retention, and adjacent BIGINT IDs. Handler tests verify scope forwarding, normalization, statuses/body and propagated failures. The new dispatch-like SQL scenarios prove lock compatibility; the existing real dispatch, service-session and resource-assessment PostgreSQL suites provide separate runtime compatibility evidence when the dedicated test URL is supplied.

Shared staff-removal `removeAssignmentsForUserAndTenant` remains an independently inventoried writer gap: lock compatibility does not prove its complete revision coverage. Tenant queue settings, account-deletion operational cancellation, configuration/plan watermarks, direct scripts/migrations and historical reconciliation retain their B2 gaps. B1 still has no live source-assessment consumer. Neither `tracking_enabled` nor `writer_coverage_complete` constraints change; producer remains `not_ready`, snapshot null. No repair, activation, plan reassignment, dashboard redesign, capture, forecast adapter or customer inference is added.

Application environment restoration was unavailable because Bitwarden was locked. No application service or external database/email target was started; tests explicitly target the disposable loopback database. Authenticated live counter-administration acceptance remains a separate deployment gate.
