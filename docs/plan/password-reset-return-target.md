# Password reset return target

Vendor PR446 review4274331130 found that a deep Vendor target, especially queue-board pairing approval, survives only when the reset page already contains next. Actual recovery emails discarded it because the request carried only email and the server generated only /login?resetToken.

The ordinary password-reset request accepts optional next in PasswordResetRequest. The route forwards it to token issuance. The service validates a bounded same-origin internal dashboard path and includes it as one encoded next query value on the trusted client login URL. Dashboard paths use literal route segments; absolute/protocol-relative URLs, backslashes, control characters, encoded path segments, traversal outside the dashboard, malformed escapes and oversized targets fall back to the existing default link. Query values and fragments remain intact. Missing and non-vendor targets keep the previous behavior, including Platform/developer resets whose callers do not opt in.

Next is a navigation hint, never authentication or authorization. Token hashing, expiry, one-use/revocation, generic account-enumeration-safe responses and post-reset normal sign-in/MFA/tenant permissions are unchanged. The target and queue pairing code are not added to token storage or security audit metadata. No schema change, provider action, production reset or production email is performed for validation.

API owns backend and the optional shared request field; Vendor owns the frontend request and post-reset redirect in446. Pair local acceptance with a captured local reset email: request from a deep target, open the generated URL in a fresh browser context, change the synthetic local password, complete normal sign-in/MFA and assert the exact original target survives. This proves navigation preservation, not physical queue-board pairing approval. New requests to older APIs retain the existing default until the API dependency ships; don't claim the full feature deployed from frontend checks alone.
