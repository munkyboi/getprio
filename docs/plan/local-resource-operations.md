# Local resource operations API

This endpoint is for an isolated synthetic local four-court demo. It does not activate production tracking, certify writer coverage, assign physical numbered courts, or make the forecasting snapshot ready.

`GET /api/vendor/tenant/:tenantSlug/locations/:locationSlug/resource-operations` uses normal authentication and current `tenant.queue.read` permission, including staff location/counter assignment. It requires a direct loopback request, explicit `LOCAL_POOL_DEMO_ENABLED=1`, `NODE_ENV=development|test`, a loopback DATABASE_URL naming `getprio_local_pool_demo[_suffix]`, matching actual database/server identity, and exactly one scoped `public.local_pool_demo_scopes` row with `fixture_key='four-court-v1'`. No migration creates that marker. Missing gates return404; denied current scope403. The actual local fixture, not repository or production schema, owns any constraint relaxation needed to exercise tracking. No copied real account credentials.

The authoritative response type is [LocalResourceOperations](../../shared/localPoolDemo.ts). Reads use a bounded READ ONLY repeatable-read transaction and a fresh authorization/marker checkpoint before returning. The endpoint sends no-store. Ledger revision is the actual scope revision; pool revisions remain separate and are not plan/configuration provenance. No synthetic ready flag is returned.

`pools` reports configured capacity, held allocation units, overdue allocation units and protected reservation units overlapping the observation. Converted reservations are not counted again. `availableUnits` is observed-now free capacity, **not admission permission for the next service's entire interval**. The existing transactional start command alone decides that. Expected end never releases occupancy. `activeSessions` includes every unreleased allocation across queue dates; `called` excludes those allocated tickets, while pending calls still occupy the counter. Unknown plans remain null; inconsistent held work yields explicit reconciliation issues and blocks advisory call controls.

`counterDispatch` reuses the existing pure counter-dispatch formatter, coherent current counters, pending calls and shared booking earliest-call predicate. It includes actual open Queue Day/deadline and active legacy closure facts; it does not derive call permission from free pool units. Advice is refreshed after every mutation/409 and does not replace current authorization or writer checks. Waiting inventory is not a claim of global eligibility/order across days. Full fixture uses one check-in counter and fungible four-unit pool; a fifth called ticket can correctly receive409 on start.

Start/complete/interrupt remain existing authenticated `POST /api/vendor/tenant/:tenantSlug/queue/tickets/:ticketId/service/{start|complete|interrupt}?location=:locationSlug`. Do not replace exact ticket IDs with “current” for session completion. Local Queue owner adjusts dispatch to disregard only started, unfinished tickets with matching held allocations. Production default dispatch remains unchanged.

Bounds are50 pools,1000 active allocations,1000 protected reservations,1000 relevant tickets,100 counters and512KiB response; overflow fails closed409 without a partial snapshot. Scoped statement timeouts apply. Fresh errors never become an empty successful inventory.
