# Vendor queue grant locking

The common `withVendorQueueTransaction` adapter now requests share locks when reading the authorized actor. After the existing location-first lock, it rereads the current user deletion/suspension state, active tenant membership and action permission. The accepted user and membership rows remain locked through commit or rollback. Staff additionally hold the accepted explicit branch assignment, or the accepted counter assignment and currently active scoped counter. An explicit assignment remains sufficient even if a separate counter assignment changes; the adapter holds the access path that actually authorized the action.

This covers explicit service timing and the shared queue-service paths for walk-in issuance, calling, confirmation, skipped restoration, called-ticket resolution and vendor waiting cancellation. Manual legacy intake already holds its own authorized grants. Revocation committed before authorization is reread and rejects the operation; concurrent updates/deletes to accepted grants wait until the authorized transaction finishes. Locks end on rollback too. Permission checks using the returned actor context, including linked-booking management, therefore use grants held for that transaction.

Activity policy remains action-specific. New service starts and open-queue actions still require current tenant/branch activity under their existing checks. Authorized explicit completion/interruption remains available after tenant/branch or timing disable to release actual occupancy. This change holds actor/access grants, not tenant activity rows; it does not certify every activity/configuration writer or eliminate database deadlocks involving other lock orders. Any transaction error still follows the existing rollback path.

Calling, confirmation and admission do not allocate resources. Explicit service start allocates, and explicit completion/interruption releases. Tracking and coverage gates stay disabled; the producer remains `not_ready`. Enforced/system lifecycle, deletion cancellation, configuration/reconciliation and complete writer inventory remain separate work. No activation, backfill, capture/export/inference or customer estimate change.

Validation uses the actual ledger/authorization/assignment/timing code with the existing minimal PostgreSQL event/booking fixtures. Barrier tests prove owner, explicit staff and counter staff grant locks, actual concurrent revocation blocking until commit, subsequent denial, and unchanged occupancy after denied completion. Additional tests cover revocation committed while waiting for the location or grant locks, rollback lock release and authorized explicit interruption on an inactive tenant/branch. These are local database proofs, not authenticated live queue execution or full production-schema lifecycle proof.

Final disposable PostgreSQL backend suite: 992 passed, seven opt-in skips (999 total), zero failures. Focused ESLint, backend typecheck and diff checks passed. Aggregate coverage: 66.11 percent lines/statements, 69.21 percent branches and 61.52 percent functions; no 80 percent threshold claim.
