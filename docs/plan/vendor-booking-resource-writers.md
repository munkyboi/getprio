# Vendor booking resource writers

Vendor status (confirm/cancel) and reschedule now enter the location-first scoped ledger transaction. Routes pass the authenticated actor. Under the location lock, active tenant membership, booking-management permission, actor deletion/suspension and booking tenant/location/arrival/state are rechecked from persisted data. Route authentication, MFA and permission checks remain in place. These mutation paths no longer run a separate bulk expiry write before authorization; confirmation/reschedule reject an expired pending booking without proof under the booking lock. Expiry reconciliation remains a separate uncovered writer.

Confirmation preserves an existing protected binding, validates its item interval, and refuses an enabled resource booking missing protection. It does not backfill or change demand from edited configuration. Cancellation cancels protected bindings by immutable booking/scope identity even after draft edits or tracking disable. Converted bindings reject both actions; neither action releases actual occupancy. Status, binding commands and location revision commit together, followed by notifications.

Rescheduling moves frozen item durations/quantities and leaves prices/item identities unchanged. Catalog service and location availability are reloaded on the transaction client and ordinary capacity is rechecked excluding the current booking. Bundle item intervals and the booking interval are updated together for parallel/sequential ordinary compositions. Reschedule slot previews use the same frozen durations and quantities; new-intake quantity/manual-payment rules do not rewrite an existing selection. Removed/inactive service selections reject.

For a protected resource booking, rescheduling first verifies the original interval and current pool/demand revisions and units. Changed resource configuration rejects as stale rather than silently changing the binding. The old protection is cancelled and a replacement is capacity-checked/inserted in the same transaction as schedule changes. A conflict rolls back the old binding, item/booking intervals, command receipts and revision. Replacement receipt keys include the old binding identity, allowing a later move back to an earlier interval without replaying a cancelled reservation. Existing protection is replaced even when tracking has since been disabled. This is not whole-request HTTP idempotency; repeated successful moves can create further immutable history.

Tracking and writer-coverage constraints remain disabled. No ready snapshot, activation/backfill, inference hook or customer estimate change is introduced. Proof/payment, expiry/no-show, check-in, session allocation/release and configuration/reconciliation still need integration before full coverage can be certified. Already-started work remains managed by explicit service-session completion/termination.

Validation uses the production scoped adapter and booking service with transactional fixture repositories, plus the actual bundle-interval repository method and ledger migration in disposable PostgreSQL. Tests cover composed frozen intervals and matching slot previews, replacement/move-back, tracking disable, create/reschedule contention, conflict rollback, stale revisions, vendor confirmation/cancellation, membership/suspension denial, missing protection, pending expiry and converted occupancy. This is not live authenticated vendor resource execution. Full backend coverage command: 847 passed, seven unrelated opt-in skips, zero failures (854 total). Backend typecheck, focused lint and diff checks passed.
